## Current Focus
Two real new architectural features shipped this session, both on branch feature/cross-document-link-resolution (off main, not yet merged - pushed and a PR is being opened): cross-document link resolution (tracking a document also tracks whatever HTML it links to, and links actually resolve and navigate in the reading pane) and per-version text highlights (select text, mark it in one of 4 colors, scoped to the exact version - never inherited by a newer one). Full detail, including three real bugs found and fixed via manual Playwright verification, is in progress.md's own two new sections for these features - read those before touching track.js, reconcile.js, server.js's handleContent(), link-discovery.js, highlight-render.js, or app.js's reading-pane message listener.

Both features were built via the full brainstorm -> spec -> plan -> TDD-implementation cycle this project now consistently follows for anything architectural, continuing directly on the same branch rather than stacking separate PRs, since the second feature (highlights) directly extends the first's own handleContent()/postMessage infrastructure rather than duplicating it.

The README was also updated with both features (new bullets under "How It Works") - neither added a new CLI command, so the CLI Reference table itself needed no change; verified against docmanager --help's actual real output to confirm no other drift.
Fixed a real, user-reported bug in per-version highlights: highlighting text via a real triple-click ("select this line") landed the Range boundary on an element container rather than a text node, and normalizeBoundary() in src/core/highlight-render.js mishandled that - either silently aborting the highlight entirely (when the resolved child was itself a bare text node, since createTreeWalker(textNode, SHOW_TEXT).nextNode() can never return the walker's own root) or, for the out-of-bounds "end of container" fallback, taking the FIRST text descendant of a multi-descendant element (e.g. a paragraph containing a link) instead of the LAST, producing a wrong-but-plausible truncated highlight. Root-caused via direct empirical confirmation in a real browser (not guesswork), fixed by resolving a bare-text-node child directly and by walking to the last text descendant for the fallback case. PR #17: https://github.com/adeeshsharma/docmanager-axi/pull/17, not yet merged.
Unified highlighting and cross-document link navigation across the reading pane and standalone tabs: "Open in new tab" now opts into the same ?render=1 rendering path the reading pane's iframe already used, so a document opened in a plain browser tab gets the same rewritten links and injected highlight script instead of raw byte-identical content with neither feature working. The injected scripts (highlight-render.js, link-discovery.js's LINK_CLICK_SCRIPT) detect their context via `window.parent === window` (true only for a standalone tab, never inside the sandboxed reading-pane iframe, which has no allow-same-origin) and branch: embedded keeps relaying through postMessage to the parent page as before; standalone calls the highlight create/remove routes directly via same-origin fetch(), and navigates its own location for cross-document links instead of opening more tabs. buildHighlightScript()'s signature changed from a bare highlights array to { familyId, hash, highlights }, since only the new standalone path needs familyId/hash to call the API directly. Also fixed, found via manual testing of this change: the highlight-remove handler only unwrapped the single <mark> element under the cursor - a highlight spanning multiple text nodes (e.g. a triple-click selection including a trailing whitespace/newline node) produces multiple <mark>s sharing one id, and removing it left the others behind client-side until reload even though the record was already deleted server-side; now every <mark> sharing that id is unwrapped. PR #19: https://github.com/adeeshsharma/docmanager-axi/pull/19, not yet merged.

## Things a fresh session must NOT assume

- **`ARCHITECTURE.md` is the source of truth for design**, not this memory - already updated post-v1 with the UI's reading-first purpose, the sandbox scoping, and batch/folder tracking. Read it fresh.
- **A real Playwright install (Chromium + bundled ffmpeg) is available and routinely used in this environment now** - every UI-facing round since the folders feature has been verified with a real, temporary `npm install --no-save playwright` (confirmed removed afterward each time - `git status` shows no `package.json`/`package-lock.json` drift), driving the actual running core and inspecting real screenshots, not just structural HTML/CSS checks. This corrects an earlier, now-stale note in this same file claiming "there is no rendering/screenshot tool available" - that was true once, it is not true anymore. Still be honest about what was and wasn't actually verified for any given change; just don't assume the capability itself is missing.
- **The UI's iframe sandbox allows scripts on purpose**: `sandbox="allow-scripts"` with no `allow-same-origin`, no `allow-top-navigation`, no `allow-popups`, no `allow-forms`. A tracked document's chart/diagram script (Chart.js, D3, Mermaid) needs to run to render at all; the isolation that matters is withholding same-origin access, not disabling scripts. Don't revert to a no-scripts sandbox without re-reading why in `ARCHITECTURE.md` section 5.
- **The "newer version available" banner uses two distinct pieces of state on purpose** (`app.js`): `viewingHash` (what's actually loaded right now) vs `lastKnownHeadVersion` (what the head was as of the last sync). Comparing against the wrong one would make browsing old versions falsely trigger the banner. Don't collapse these into one variable.
- **Framework question is settled**: stay framework-free for the UI. The visual redesign is pure CSS/HTML/hand-written SVG, no framework or bundler pulled in, consistent with every prior decision on this.
- **`track` takes multiple paths and expands folders recursively**, wire format `{paths: [...]}` returning `{results, summary}` - a clean redesign, not a versioned/back-compat change, since nothing was published when it changed. A folder-discovered file's synthetic path comes from its location relative to the tracked folder's root, not just its basename. (Note: this is filesystem folder-walking during `track`, a different concept from the docmanager *folders* feature above, which organizes already-tracked documents and has nothing to do with the real filesystem.)
- **The suggestion-vs-automatic-vs-behind-head version-capture distinction is load-bearing** (see `technical/patterns.md` and `technical/techContext.md`'s phase 5 findings): a change at an already-tracked path is captured automatically; a newly noticed, previously untracked file that merely resembles an existing family is only ever suggested; a tracked file whose content matches a KNOWN EARLIER version, not the current head, is `behind-head`, purely informational, never written.
- **Every module that touches storage must go through the core process** - `store.js`'s single-writer queue only serializes within one process's lifetime, which is why the CLI and UI are both thin clients to the core rather than shortcuts. Confirmed empirically multiple times now, not just asserted.
- **The core stops itself after a long idle period now, and can be stopped directly from the UI** - this was a deliberate reversal of the original v1 "no idle timeout" decision, made after the user weighed the tradeoff directly, not an oversight being corrected. `src/core/shutdown.js` is the one canonical shutdown path; don't add a fifth place that calls `server.close()`/`closeAllConnections()` directly, route any new shutdown trigger through `requestShutdown()` instead.
- **An Agent Skill now exists** (`skills/docmanager/SKILL.md`, generated from `src/skill.js`) alongside the session-start hooks - they're complementary, not redundant, per the `axi` skill's own guidance. If the CLI's real behavior changes, update `src/skill.js`, not the committed `SKILL.md` directly, and re-run `npm run build:skill`.
- **Folder tracking excludes vendor/build directories by name** (`EXCLUDED_DIR_NAMES` in `track.js`: `node_modules`, `.git`, `.hg`, `.svn`, `.docmanager`, `dist`, `build`, `out`, `.next`, `.nuxt`, `.cache`, `coverage`), applied in both the plain-directory and symlinked-directory branches of the recursive walk. This is load-bearing, not cosmetic - a real accidental whole-Desktop track pulled in hundreds of unrelated `.html` files from `node_modules` trees before this existed. Don't remove or narrow this list without a real reason.
- **`untrack` exists now** (`docmanager untrack <id>...`, `POST /documents/untrack`, a UI button) - it removes a family's version history from docmanager only, never the real file on disk. Built because the whole-Desktop mistake above proved "undo a tracking mistake" is a real, not hypothetical, need.
- **A real `test/` suite exists** (`node:test`, run via `npm test`, 182 tests as of the folders feature) - any change to `store.js`, `track.js`, `reconcile.js`, `snapshot.js`, `folders.js`, or the CLI should be checked against it before considering the change done, and a genuinely new behavior should get a new test, not just a manual check. Don't fall back to throwaway scratch scripts as the only verification for these modules.
- **`docmanager doctor` (`src/core/doctor.js`) and the duplicate-suggestion heuristic (`src/core/suggest.js`) auto-repair only what's provably safe** (a derived index rebuild, a mapping/reference to a *genuinely gone* family or folder) and only ever report anything that could be real data loss - never extend it to auto-fix a corrupt family record or a missing content blob without a real conversation about that boundary first, it's deliberate, not an oversight.
- **Any code that loops over `listFamilyIds()` calling `getFamily(id)` must guard each call with its own try/catch**, skipping just that one family on failure. This is not a hypothetical - a single corrupt family JSON file previously crashed `rebuildIndex()`, `suggestLinks()`, and `reconcile()` entirely, taking down the whole app for every other healthy document. Keep this pattern in any new code that walks all families (or all folders).
- **Revert (`revertToVersion` in `store.js`) only ever moves `headVersion` to an existing hash - it never creates a new version entry.** This is not a stylistic choice, it's forced by the content-addressed model: content hash is deterministic, so "reverting" to old content can never produce a genuinely new, distinct version identity, only collide with the hash that content already has. Do not "fix" this into creating a new entry per old-content bytes without re-deriving why that would corrupt the colliding entry's own `createdAt`/`supersedes` fields.
- **Diff (`src/core/diff.js`) runs on normalized content, per `ARCHITECTURE.md` section 3.4** - reuses `normalizeHtml()` from `html-normalize.js` unchanged, plus a separate, display-only `prettyForDiff()`. Don't diff raw bytes directly; a whitespace-only difference between two versions must never render as a fake change.
- **Search (`src/core/index.js`'s `search` FTS5 table) is explicitly keyword, not semantic** - it exists specifically so "where's the document about X" doesn't have to wait on embeddings, but it will never find a document by meaning alone. Don't blur this distinction in UI copy or docs; RAG/semantic search stays a deferred, separate phase-2 goal.
- **`extractTitle`/`extractPlainText` live in `html-normalize.js`, shared by `suggest.js` and `index.js`'s search indexing** - if a third caller ever needs "what does this document call itself" or "its visible text," import these rather than writing a third copy. `extractPlainText` deliberately excludes the entire `<head>` subtree, not just `<script>`/`<style>`.
- **`deleteVersion` (`store.js`) must always heal the supersedes chain, never leave a dangling pointer.** Any future change to this function has to preserve: re-linking whoever superseded the deleted version to its own parent, moving `headVersion` back to that same parent when deleting the current head, refusing on a family's last remaining version, and never touching the content blob.
- **Any server.js route the UI consumes directly (not via a follow-up `GET /families/:id` re-fetch) must return `family` from `getFamilyFromIndex()`, never a mutation function's raw store.js return value.** `store.js` represents `versions` as a hash-keyed object; the UI (`app.js`'s `renderTimeline`/`populateCompareSelects`) expects the array shape the index produces. Check this explicitly for any new mutation route.
- **`docmanager setup ssh` (`src/core/ssh-check.js`) must stay strictly read-only - never write to `~/.ssh`, never call `ssh-keygen`.** This is a hard rule in `AGENTS.md`, the same class as the pre-existing git-install approval-gating rule.
- **`GET`/`PUT /settings` must never echo `snapshotRemoteToken`'s real value - only `snapshotRemoteTokenSet`.** The redaction lives in `server.js`'s `redactSettings()`, not in `settings.js` itself (which `snapshot.js` needs the real value from). Any new route or field that touches settings needs the same boundary discipline.
- **The rendered diff (`renderHighlightedContent` in `diff.js`) is deliberately block-level, not word-level - don't "improve" it into word-level highlighting without re-deriving why.** Only ever adding a `data-diff` attribute to an element that already exists in the tree is what makes this safe by construction.
- **The compare view is a full-screen modal (`#compare-modal`), not an inline panel.** Reuse its CSS (`.modal-overlay`/`.modal-dialog`/`.modal-header`/`.modal-close`) for any new modal need - the folder-picker and folder-context-menu both already do.
- **Scroll sync between the two comparison iframes works via `postMessage`, not direct DOM access - this is a hard constraint, not a choice.** The sandbox (`allow-scripts`, no `allow-same-origin`) means the parent page cannot read or set either iframe's scroll position directly.
- **The rendered diff's `REMOVED_CSS`/`ADDED_CSS` in `diff.js` use `!important` deliberately - one of a small, explicitly-reasoned set of exceptions to this project's own no-`!important` stylesheet discipline** (alongside the global `[hidden]` fix in `style.css`). It's forcing a readable text+background color pair onto content whose own CSS is completely unknown and unpredictable - not a specificity-fight shortcut.
- **`docmanager core start`/`docmanager ui` serve `dist/ui` over `src/ui` whenever `dist/ui` exists** (`server.js`'s `uiAssetsDir()`). `dist/` is gitignored build output from `npm run build`, and node caches modules per-process, so editing `src/ui/*` alone does nothing to a core process already running against a stale `dist/`. Any UI-visible change needs `npm run build` AND a core restart before it's reachable for manual verification.
- **A family's `syntheticPath` is denormalized in `local-state.json`'s mapping entries and in `family.title`'s default, and both must be kept in sync on rename.** `reconcile()` echoes a mapping's own `syntheticPath` directly in every result; `renameFamily` also updates `title` when it still equals the old path.
- **Tags are a plain `family.tags: string[]`, whole-array-replace only** (`setFamilyTags` in `store.js`) - the CLI's `--add`/`--remove` flags compute the new array client-side and send a full replace. `index.js`'s `search` FTS5 table indexes tags space-joined into their own column.
- **The Lavish Editor integration has no "session" concept in docmanager itself, and must not grow one.** A working copy exported for editing is deliberately never added to `local-state.json` - that absence IS the mechanism that keeps intermediate edits from being auto-captured.
- **`docmanager families lavish <id> <hash>` is the real, current entry point for the Lavish workflow.** `lavish-axi` is a genuine `package.json` dependency, resolved via `src/cli/lavish.js`'s `resolveLavishCli()` and spawned directly - no `npx` anywhere at runtime. Working copies live under `paths.js`'s `editDir()`.
- **`--relink` is a general "reattach a real file to an existing family" mechanism, not a snapshot-specific one.**
- **Every commit and every push still needs its own explicit, in-the-moment request** - a prior approval doesn't carry forward to the next change. `.gitignore` deliberately excludes `docs/`, `AGENTS.md`, `CLAUDE.md` (matching reactive-axi's own setup); `.memoryintel/` is deliberately *not* excluded - it's meant to be git-committed, unlike the retired `memory-bank/` folder.
- **`ensureCoreRunning()` restarts a core whose reported `/health` version doesn't match the CLI's own, on every invocation.** `docmanager core status` surfacing `stale`/`version` is deliberately read-only - it never itself calls `process.kill`.
- **The theme attribute (`data-theme` on `<html>`) and the sidebar-collapsed attribute (`data-sidebar-collapsed`) are both set in exactly one place: a synchronous inline `<script>` in `index.html`'s `<head>`, not in `app.js`.** Both are deliberate anti-flash design - `app.js` loads at the end of `<body>`, well after first paint. `app.js` only reads `localStorage` once at startup to sync each control's own visual state to whatever the head script already applied.
- **The sidebar's `--sidebar-*` CSS variables are deliberately untouched by the theme toggle - the sidebar stays a fixed dark chrome regardless of System/Light/Dark**, and independently, the sidebar-collapse toggle (`docmanager-sidebar-collapsed` in `localStorage`) is a separate, unrelated display preference from the theme.
- **`reconcile.js` must always read `syntheticPath` from the freshly-loaded `family` record, never from a mapping's own cached copy.** `local-state.json` is deliberately never synced.
- **The UI is not "read-only end to end."** No tracked document's actual HTML *content* is ever editable through the UI (that stays Lavish Editor's job), but docmanager's own metadata about a document - which version is current, its synthetic path, its tags, its folder, whether it's tracked at all - is fully manageable from the UI.
- **`.icon-button` is now shared between real `<button>` and `<a>` elements across the whole document-detail toolbar** (rename, move-to-folder, untrack, revert, compare, open-in-tab, download, edit-in-lavish) - it carries an explicit `appearance: none; text-decoration: none; background: none;` reset for exactly this reason, the same class of bug this project already hit once for `.open-in-tab` alone. Don't add a new icon-style `<a>`/`<button>` pair without checking this reset still covers it.
- **`[data-tooltip]` is a CSS-only, fast custom tooltip mechanism (`attr()`-driven `::after` content, ~150ms) replacing the browser's native `title` attribute delay** for every icon button in the document-detail toolbar. It renders above its trigger by default; `.detail-identity-row [data-tooltip]::after` specifically overrides to render below, since that row sits flush against `.detail`'s own `overflow: hidden` top edge and a tooltip rendered above it there gets clipped. Any new icon button added to that specific row needs the same below-rendering treatment, not the default above-rendering one.
**A local-state mapping inside `editDir()` is always a single-use Lavish scratch copy, never a second genuine tracked location - `trackPath()`'s relink branch (`track.js`) now enforces this by retiring a family's PRIOR `editDir()` mapping (and deleting its file) every time it relinks to a new one.** This was a real bug: before the fix, a second Lavish session on the same document left the first session's abandoned working file permanently mapped, which made `deleteVersion`'s live-content check (`store.js`) wrongly refuse to delete a long-superseded version. Don't revert this retirement logic without re-deriving why - it's scoped narrowly to `editDir()`-nested paths so it never touches a family's original tracked file or any other legitimate second real-world location.
- **GET /content/:hash serves TWO fundamentally different consumers and must keep telling them apart.** Bare (GET /content/:hash, no query param) must always return byte-identical original content - families export, families lavish (materializing a version for Lavish Editor), and the UI's own "Open in new tab"/"Download" all depend on this. Only ?render=1 (sent exclusively by the reading pane's own iframe via viewVersion() in app.js) triggers cross-document link rewriting and highlight injection. Getting this backwards once already broke families export in practice, caught by this project's own test suite - don't add a THIRD content-modifying feature to handleContent() without checking this gate is still respected.
- **A highlight's stored coordinate is a flattened-visible-text character offset, never a DOM structural path.** This is load-bearing, not a style choice: <mark>-wrapping text never changes any OTHER character's offset, which is exactly what makes independent create/remove of multiple highlights on one version safe without a renormalization step whenever one is deleted. Don't "simplify" this back to an element-child-index path without re-deriving why that was rejected during brainstorming.
- **Any script injected via injectIntoHead() executes synchronously at its own injection point - before the rest of the document's real content exists in the DOM.** A document.body truthiness check is NOT sufficient (body exists with zero children at that point); anything that needs to walk/mutate the document's actual content must defer to DOMContentLoaded unconditionally. Event-listener REGISTRATION itself is always safe immediately (nothing needs the DOM until a real user interaction fires the callback later) - only code that runs eagerly at the top level needs this guard.
- **linkRoot (on a local-state.json mapping) bounds cross-document link-following the same way collectHtmlFiles()'s own EXCLUDED_DIR_NAMES bounds folder-tracking - both exist because of the SAME real incident** (a whole-folder accidentally tracked, pulling in unrelated files). A link resolving outside its linkRoot, or a mapping with no linkRoot at all (a project that predates this feature), is always treated as "can't verify, skip" - never guessed at, never auto-expanded.
