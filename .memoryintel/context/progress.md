## Fifth round: the actual root cause of the reconnect banner was the dynamic port itself

The two lifecycle fixes above were real bugs, but neither actually explains why the user kept seeing the reconnect banner across multiple supposedly-fresh tabs. The user asked directly why docmanager doesn't just always use the same port, checking first whether one is already running - which is exactly right: the singleton check already existed, but the daemon still bound a randomly OS-assigned port on every fresh start, so any tab is only ever valid for one specific daemon instance and breaks the moment it restarts for any reason. Fixed by switching to a **fixed default port, `4389`**, continuing lavish-axi (`4387`) and reactive-axi (`4388`)'s own convention, falling back to a random port only if `4389` is genuinely taken by something unrelated. Verified directly across a fresh start, a simulated crash-and-restart, a normal stop-and-start, and a deliberate port-conflict scenario - all landing correctly. Full detail in `techContext.md`.

## Sixth round: idle SSE timeout and an over-eager banner, after the port fix still didn't resolve it

The user confirmed they were on the correct, stable port on a fresh tab and still saw the banner - ruling out every hypothesis tried so far. Two direct checks against the live daemon (a plain connection, and one with a browser-realistic matching `Origin` header) both succeeded, ruling out an Origin-check false positive too. The gap neither check exercised: real elapsed time - both only held connections open for a second or two. Root cause: the server sent one `:\n\n` comment on connect and nothing else unless a document actually changed, so a connection could sit completely idle indefinitely, which browsers/OS network stacks/local proxies are known to close. Fixed with a 20-second heartbeat, verified by holding a connection open 25 seconds and confirming the exact expected bytes arrived. A compounding client-side issue was also fixed: the banner appeared on the very first connection error even though `EventSource` auto-reconnects on its own, so even a routine, self-healing blip looked like a permanent failure - now there's a 4-second grace period before the banner shows at all, cancelled immediately if the connection recovers. Four real, independently-verified fixes came out of this one user-reported symptom across two rounds (orphaned daemons, a hanging stop, a dynamic port, and now this) - full detail in `techContext.md`, including the honest note that whether this is genuinely the end of it still needs the user's own confirmation.

## Real bug found through actual use: deleting a version resurrected it

The user found this by actually using the Lavish workflow, not from testing: a version created at the end of a Lavish session couldn't be deleted - delete it, and a new version with the exact same content came right back. Root cause: `deleteVersion()` never touches the real file on disk, and `reconcile()`'s only way to tell "genuinely new content" from "an already-known older version" is a lookup by content hash in `family.versions` - which the delete itself just removed. So the next reconcile silently re-captured the deleted content as a brand-new version. An existing test had explicitly asserted this resurrection as intentional, correct behavior at the time it was written (avoiding silent data loss) - shown to be wrong in practice, since it silently undid the user's actual intent instead. Fixed: `deleteVersion()` now refuses (`VERSION_STILL_LIVE`) if any live, locally-mapped file still holds the exact content being deleted, naming the real path in the error. Wired through server/CLI error handling; the old test rewritten to assert the refusal plus a follow-up confirming deletion succeeds once the file is edited to differ. Full suite 145/145. Manually verified end to end against a real isolated CLI instance reproducing the exact scenario; real `~/.docmanager` store confirmed untouched. All docs updated.
