## Decisions Log
2026-09-13: Per-version highlights now cascade forward automatically when a new version is captured (recordVersionIfChanged in store.js), re-anchoring each highlight by exact substring search in the new version's own flattened visible text (extractFlattenedVisibleText(), new in html-normalize.js) rather than trusting the old character offsets directly; a highlight whose exact text was edited away is dropped, not guessed at, and ties (the same text appearing more than once) resolve to the occurrence closest to the original offset. This SUPERSEDES the original 2026-08-31 per-version-highlights design decision that highlights were 'scoped to the exact version they were made on... never inherited by a newer version' - that was a deliberate v1 scoping choice, not a technical constraint, and the user explicitly asked for it reversed. No server.js or UI change was needed: handleContent() already reads a version's highlights straight off the store record, so anything the new remapHighlights() writes there renders automatically. Covered by 6 new tests in test/store.test.js and 3 new tests in a new test/html-normalize.test.js; full suite 243/243.
2026-09-13: Automatic version capture (recordVersionIfChanged in store.js) is now debounced - a save landing within settings.versionDebounceSeconds (fixed enum 5/10/15/20/30/45/60, default 20, configurable via `docmanager settings set --version-debounce` or the UI Settings page) of the current head's own createdAt amends that head's slot in place instead of stacking a new version, refreshing createdAt on every amend for a true trailing-edge debounce. Direct user request: rapid AI/human saves a few seconds apart were each becoming their own permanent version. DECISION, found necessary mid-build via this project's own sync.test.js failures: the family's ROOT version (supersedes: null) is NEVER amended, regardless of timing - its first edit always becomes a real, permanent version. Reasoning: two machines that independently pull the same root and then each edit it within the debounce window would otherwise each amend their own local copy of the root away, leaving sync.js's unionFamilyVersions() with no shared version hash to recognize as a common ancestor - reproduced concretely as 3 real test failures (sync.test.js's Case A tests) before the guard was added, not a hypothetical concern. Every non-root version stays fully debounce-eligible; an amend always preserves whatever its own parent already was, so the root alone is guaranteed to survive as a shared anchor for any two forked histories to merge back against. A second, unrelated fix was needed to make the default-on debounce not break ~26 pre-existing tests that record several versions of one family in quick real-time succession as scaffolding: a DOCMANAGER_VERSION_DEBOUNCE_MS env override (store.js) in the same style as daemon.js's existing DOCMANAGER_IDLE_TIMEOUT_MS, zeroed by default in test/helpers.js's useIsolatedHome() for every in-process test file and in test/cli.test.js's shared subprocess env - store.test.js explicitly un-zeroes it in its own beforeEach since it's the one file that tests the real debounce timing (via node:test's built-in mock Date timers).
