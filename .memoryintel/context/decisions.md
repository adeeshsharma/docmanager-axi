## Decisions Log
2026-09-13: Per-version highlights now cascade forward automatically when a new version is captured (recordVersionIfChanged in store.js), re-anchoring each highlight by exact substring search in the new version's own flattened visible text (extractFlattenedVisibleText(), new in html-normalize.js) rather than trusting the old character offsets directly; a highlight whose exact text was edited away is dropped, not guessed at, and ties (the same text appearing more than once) resolve to the occurrence closest to the original offset. This SUPERSEDES the original 2026-08-31 per-version-highlights design decision that highlights were 'scoped to the exact version they were made on... never inherited by a newer version' - that was a deliberate v1 scoping choice, not a technical constraint, and the user explicitly asked for it reversed. No server.js or UI change was needed: handleContent() already reads a version's highlights straight off the store record, so anything the new remapHighlights() writes there renders automatically. Covered by 6 new tests in test/store.test.js and 3 new tests in a new test/html-normalize.test.js; full suite 243/243.
