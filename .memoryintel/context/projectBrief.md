**docmanager-axi** (working name, unconfirmed for publish) helps a user manage the sprawl of HTML documents that accumulate on their machine over time — many files that are really the same document at different points in its life, with no system tracking which one is current or how it got there. It manages and versions HTML documents; it does not edit them (that's [lavish-axi](https://github.com/kunchenguid/lavish-axi)'s job).

Ships as a single npm package, run entirely on the user's own machine, bound to loopback only — same distribution model as `reactive-axi` and `lavish-axi`.

Every "which version of this HTML is actually current" question turns into hunting through a downloads folder full of `report-final-v2-ACTUAL.html`. **docmanager-axi** tracks HTML documents the way git tracks code: point it at a file once, and every real edit becomes a new version automatically - no commit step, no confirmation, nothing to remember. It runs entirely on your own machine.

- **Agent-first** - the whole surface is a CLI your coding agent drives directly: TOON output, structured errors with real exit codes, idempotent commands. A local web UI exists too, for you to read documents and browse history by hand, but the CLI is the primary interface.
- **Local-first** - no server, no account, no cloud component of any kind, unless you deliberately point it at a git remote you control for cross-machine sync.
- **Automatic, not automated-guessing** - a change to a file you already told it to track becomes a new version with no confirmation needed, since there's nothing ambiguous about it. A newly noticed file that merely *resembles* an existing one is only ever suggested, never auto-linked - that connection is always your call.
- **Real history, not a snapshot** - every version is content-addressed and kept, diffable and revertible, synced across machines through a git remote you already trust.

docmanager-axi is an [AXI](https://axi.md), which means -

- It's just a CLI any capable agent can run once installed - no special SDK needed on the agent's side.
- It's optimized for agent ergonomics: TOON output, structured errors with real exit codes (`0` success, `1` error, `2` usage error), idempotent mutations (tracking an already-tracked file is a no-op, not an error), and it fails loud on an unrecognized flag instead of silently ignoring it.
- The Agent Skill and the session-start hook are how an agent actually learns the tool - the skill for on-demand loading in any agent that supports the format, the hook for ambient context at the start of every session so a fresh agent already knows what's tracked without being told.

Source: agent-native.com/docs &middot; built by Builder.io &middot; read 2026-08-22 Overview Architecture In one paragraph You write your app's logic once, as a typed function called an action. Agent-Native turns that one function into a UI hook, an agent tool, an HTTP endpoint, a CLI command, and an MCP tool, automatically. The point is not the agent. The point is that today, most teams build a UI and a set of agent tools as two separate things, and the two drift apart as the app changes. Agent-Native makes them the same thing, so a person clicking a button and an agent calling a tool run identical code, against the same database, with no sync layer between them. The problem it is answering Bolt an AI agent onto an existing app and you usually end up building two implementations of the same behavior: one for people, through the UI, and a second, thinner one for the agent, through a hand-written set of tools. The docs put it plainly: If the agent gets a smaller, separate set of tools, it stays constrained, and the two implementations drift as the app changes. People still need a real UI. Chat is fine for delegating a task, but not for browsing, comparing, or reviewing. Work has to move between the two. A person should be able to inspect or correct what the agent did, and the agent should be able to pick up from there without starting over. Agent-Native is a set of rules an app follows so those three things fall out for free, instead of being rebuilt by hand for every feature. The core idea: one action, every surface An action is a typed function, defined once, that is simultaneously an agent tool, a React hook, an HTTP endpoint, a CLI command, and (if you expose it) an MCP or A2A tool. Here is the actual shape, from the framework's own starter template: actions/hello.ts export default defineAction({ description: "Return a friendly greeting.", schema: z.object({ name: z.string().default("world").describe("Name to greet"), }), http: { method: "GET" }, run: async ({ name }) =&gt; { return { message: `Hello, ${name}!` }; }, }); description is what the agent reads to decide when to reach for this. schema validates the input, in Zod, and doubles as the tool's typed signature. run is the actual logic, and it is the only place the logic lives. Ask the agent to call hello for a name, and it fills the schema and runs exactly this function. Add a route that calls useActionQuery from a form, and a person triggers the same function through a button. Nobody writes the greeting logic twice. Because the agent and the UI hit the same tables through the same actions, there is nothing to keep in sync by hand. The framework also gives the agent a live feed of what the person is currently looking at, the open page, the selected record, so a request like "fix this one" resolves correctly. Part 1: how it fits together Part 2: build-from-scratch spec Part 1: how it fits together Strip away the product, and the architecture is a registry of typed operations sitting in front of one shared database, reached through a handful of thin adapters, with a permission check that runs on every call. Nothing in that sentence requires TypeScript, React, or SQL specifically. Those are this framework's own choices, not the architecture's requirements. Five rules carry the whole design Reading through the actual documentation, everything else follows from five commitments. None of the five is exotic alone. What is unusual is enforcing all five as a hard contract, everywhere, starting with the first feature, instead of treating them as good practice to get to eventually. 1 One operation, one implementation Every capability the system offers is defined exactly once, in a shape both a UI and an autonomous caller can invoke without translation. That shape bundles four things: a stable id, a description written for whoever decides when to use it (a person skimming a menu, or a model choosing a tool), a schema that validates input and doubles as the tool signature handed to a model, and a handler that is the only place the logic lives. A UI button and an agent tool call resolve to the same handler, with the same validation, every time. Why not the obvious alternative: two codebases, a REST or GraphQL API for the UI and a separate hand-written tool layer for the agent, is faster to start. It also guarantees drift, because nobody remembers to update both when a rule changes, and by the tenth feature the two have quietly diverged. 2 One shared store, written by both callers directly There is no separate agent database and no cache to keep synchronized. The UI and the agent read and write the same rows. A relational store holds everything: a few system tables present in every build (ambient UI state, settings, credentials, sessions) plus whatever domain tables the product needs, defined with the same schema tooling. Because both callers reach the same tables through the same operations, a change either one makes is visible to the other on its next read, with nothing to reconcile. Why not the obvious alternative: giving the agent its own read replica, or a periodic export, is simpler to bolt on later, but reintroduces exactly the lag and staleness this architecture exists to remove. 3 The system always knows what the human is looking at "What is the user looking at right now" is not a side channel or a prompt trick. It is a row in the shared store, written on every navigation change and read before the system acts. The UI writes a small record, a view name plus whatever identifies the object (a thread id, a record id), on every navigation change. Before running any operation on the human's behalf, the system reads that record first. The channel runs both ways: a write to the same record can move the UI somewhere, so control flows through one mechanism instead of two. Why not the obvious alternative: without this, "fix this one" only resolves if the person spells out which one, every time, because the system otherwise has no notion of "this." 4 Every write becomes a versioned event Readers subscribe to staleness, not to a timer. When either side writes, a counter tied to that data increments and an event carrying the new version and who caused it goes out. A push channel delivers this instantly where one is open. A poll, asking "what changed since version N," is the fallback for anything a push channel cannot reach: a serverless function, a cron job, a second browser tab. Because every event carries who caused it, a client can ignore the events that echo its own write and skip re-fetching data it already has. Why not the obvious alternative: a plain polling interval is the natural first build. It is either too slow to feel live or wasteful when nothing changed, and it still needs version and source metadata eventually to stop self-refetch flicker, so building the counters and event tagging from the start costs little more than building the poll alone. 5 Access control belongs to the operation, not a wrapper around it Every operation carries two independent checks: which callers may reach it at all, and whether this specific caller passes. A static allow-list per operation names which surfaces may call it, an internal maintenance operation might permit only the UI and never the agent or an external API. A second, dynamic check runs on every call, given the caller's identity, role, and originating surface, and can approve, deny, or throw. Both checks run before the handler, never after. Why not the obvious alternative: bolting permission checks onto a shared HTTP layer after the fact leaves every new operation unprotected until someone remembers to add one. Making the check part of the operation's own definition makes an operation without one visibly incomplete, not silently open. Registry, adapters, and shared store One operation registry generates a UI adapter, an agent adapter, and an external adapter. All three read and write one shared state store beneath them. Operation registry one schema + handler per capability UI adapter typed hook, same schema Agent adapter same schema, as a tool HTTP &middot; CLI &middot; MCP &middot; A2A same schema, translated Shared state store one relational database, read and written directly One registry generates every adapter; nothing downstream re-implements the operation. Every write to the store also bumps a version counter and emits a change event tagged with who made it, so adapters know what went stale without polling the data itself. What this buys you, and what it costs You stop maintaining two implementations of the same behavior, and you stop shipping features the agent cannot see or the person cannot inspect. That is the whole payoff, and it is real. The cost is that you take on the live-sync plumbing, the discipline of writing every operation through the shared schema even when a quick direct database call would be faster to type, and the temptation to skip the authorization check on an operation that only looks read-only today. None of the five rules is expensive alone. Skipping one occasionally is what makes the other four stop paying off. The operation contract language-agnostic interface Operation { id: string // stable, unique description: string // tells a reader (human or model) when to use it inputSchema: JSONSchema // validates input; also the tool signature handler(input, ctx): Result // the only place the logic lives sideEffect: "read" | "write" | "approval" surfaces: Set&lt;Surface&gt; // static allow-list, e.g. {"ui","agent"} authorize(ctx): boolean // dynamic per-call check } Ctx { callerId, role, surface, // who is calling, and through what requestSource, // tab or process id, for self-write filtering focus // current "navigation" row, read before handler runs } sideEffect drives more than an audit log. "read" never triggers a change event. "write" always does. Registry and adapters On boot, scan every operation definition once and register one adapter per declared surface. Every adapter, regardless of surface, runs the same five steps. Only the parsing in step 1 and the serialization in step 5 differ by surface. Parse the incoming call (an HTTP body, a CLI argument list, a model's tool call) into raw input plus caller identity. Validate the input against inputSchema . Reject before the handler ever runs. Build the full ctx , including a read of the caller's current focus from app_state . Check surfaces for this adapter, then run authorize(ctx) . Deny closes the call here. Run the handler. If sideEffect is not "read" , bump the affected scope's version and emit a change event tagged with requestSource , then serialize the result back through this adapter's convention. No adapter re-implements the operation. Each one only translates a calling convention in, and a result back out. 4. Context-awareness protocol On every navigation or selection change, the UI writes to app_state under the reserved key, tagged with its own requestSource . Before any operation acts on the human's behalf, the dispatcher reads that same key and injects it into ctx.focus . A reserved operation lets the agent write to the same key, which moves the UI, so both directions go through one channel instead of a separate command path. 5. Live sync protocol Every non-read operation bumps change_versions for the scope it affects and emits { scope, version, source } . A push channel (SSE or a WebSocket) delivers the event immediately to connected clients. A poll endpoint, "what changed since version N," is the fallback for anything the push channel misses: a dropped connection, a serverless invocation, a background job. Because it asks by version rather than requesting everything, a client that reconnects after a gap catches up in one request. A client refetches only the scopes it actually depends on, and skips any event whose source matches its own requestSource , since it already applied that write locally. 6. Access control defaults Deny by default. An operation with no declared surfaces is callable by nothing; an operation with no authorize function should fail to register, not silently allow everyone. Both checks in step 4 of the adapter run before the handler, never as an afterthought wrapped around it. 7. Why it exists Markdown workflows have largely shifted to HTML. Anyone who iterates on a document, by hand, with an editing tool, or with an agent, tends to end up with a folder full of files that are really one document at different points in time: report.html , report_v2.html , report_final.html , report_final_ACTUAL.html . Nothing on the filesystem records which one is current, how they relate, or what actually changed between them. This gets worse over time, and worse again once the same person works from more than one machine. Existing tools in this same family solve a related but different problem. Lavish Editor lets a human annotate and iteratively edit a static HTML file with an agent. Reactive-Axi does the same thing for a live running app. Neither one helps once the editing session ends and the output becomes just another file sitting in a folder, indistinguishable from nine other versions of itself. docmanager-axi is the missing piece: it manages what happens to a document after it's created, the way source control manages what happens to code. What it is, and what it is not It is A version manager for HTML documents, purpose-built the way git is purpose-built for code. A single place to read your tracked documents, the way opening a page in a note-taking app works, not just a changelog you still have to leave to actually read anything. Something you or your agent explicitly tell to track a file. Something that captures a new version automatically once a file is being tracked, with no confirmation needed. A way to carry your document history between machines through a git remote you already control. A tool an agent can drive directly through its CLI, on your behalf. It is not An editor. A document's actual HTML content is never modified through docmanager - the UI's rename, tag, revert, and untrack actions all change docmanager's own metadata about a document, never its content. You change a document with whatever tool you already use, docmanager just notices, that is Lavish Editor's job. A search engine, yet. Semantic search over your documents is a deliberate phase 2, not built here. A hosted or multi-user service. One user, one machine at a time, sync happens through a remote you already trust. A background watcher. It has no live filesystem monitor in this version; it checks for changes when something asks it to, not continuously. A tool that guesses relationships between documents on its own. It may gently suggest a link later; it never creates one without being told. This process is the only thing that ever writes to your document store. Everything else, the UI and the CLI both, are just clients that ask it questions and tell it what to do. This single-writer design is not incidental: it is what makes it safe for you to have the UI open in a browser tab while your agent is also running docmanager commands at the same time, without either one corrupting the other's work. It always runs at the same address, 127.0.0.1:4389 , rather than a different one every time it starts. This matters more than it sounds: a fixed address is what lets a browser tab you already have open keep working across a restart, instead of quietly breaking the moment the background process comes back up somewhere else. It also checks on itself periodically, so if its own registration ever goes missing or gets taken over by something else, it shuts itself down cleanly instead of lingering as an invisible leftover process. It also notices its own age: an npm update can put newer code on disk while this background process keeps running the older code it already loaded into memory, since nothing can make a running process reload files out from under it. Every command checks the running process's own reported version against the version actually installed, and if they've drifted apart, restarts it automatically before doing anything else - so an upgrade is never silently half-applied. You never have to remember to stop it. It stops itself automatically after a long period of no activity, so starting it once and forgetting about it doesn't leave anything running forever. Having a browser tab open counts as real activity on its own, so it never shuts down mid-use. You can also stop it immediately whenever you want, from the Settings page or with docmanager core stop - either way, the next command from you, an agent, or the UI starts it again automatically. The store Underneath, your tracked documents live in a real git repository, hidden away in a folder called .docmanager in your home directory. Every version of every document is a git commit. This is a deliberate choice: rather than inventing a new way to store history and diff files, docmanager reuses git, the same tool that already solved this problem well for source code. A small local database sits alongside it purely for fast lookups; it is disposable and gets rebuilt from the git repository whenever needed. That same repository is exactly what a snapshot push and pull move around, which makes it worth being precise about what it actually contains. Included, always: the real content of every version of every tracked document, and the full lineage connecting them. Never included: which real files on which machine those documents came from, or any of your local settings, including the remote URL itself. That split is what makes the sync model work at all across different machines with different file layouts, and it also means the remote is only as private as you make that repository. The UI A plain web page, no framework, no build step, served by the core service itself and opened in your normal browser with docmanager ui . It shows what's tracked, and covers everything from finding a document to safely editing one: Search. A search box above the list matches a tracked document's path, title, and actual text, showing a highlighted snippet of where it matched. Clear the box to return to the normal list. Tracking a new file or folder. A path field (not a file upload, since a browser can never expose a picked file's real path) starts tracking a file or folder directly. Pointing it at a folder only picks up HTML files that belong to you - vendor and build directories like node_modules , .git , and dist are skipped automatically. If the path already matches a document docmanager knows about, it shows you exactly which one (name, version count, last touched) and lets you decide: link this file to that history, or track it separately. Reading a document. A version timeline and a reading pane render the actual content of whichever version you select, current or past - reading is the point, the timeline is just how you get to the right version. If a new version arrives while you're reading (an edit made elsewhere), the pane never swaps out from under you mid-read; a small banner appears instead, and switches only when you click it. Managing a document. An "Untrack" button removes a document you tracked by mistake - it deletes docmanager's version history, never the real file on disk. A pencil icon renames a document's synthetic path without losing history, and tag chips attach free-form labels like "draft" or "final" that search also matches on. Checkboxes on each row let you untrack several documents at once, the same batch operation the CLI's own untrack supports. Comparing versions. A "Compare versions" button opens a dedicated full-screen view where you pick any two versions and see what changed, two ways: "Text" is a real colored line diff on normalized content, so indentation alone never shows up as a fake change; "Rendered" shows both versions as actual pages side by side, with changed paragraphs, list items, and headings highlighted in GitHub's diff colors and text forced readable regardless of the document's own theme. Both sides scroll together, and highlighting is block-level rather than word-level, a deliberate trade-off against broken-looking output. Editing a version. A "Download" button saves whichever version you're viewing as a file. An "Edit in Lavish" button copies a ready-to-paste message naming that exact version for your coding agent - docmanager has no ongoing connection to any agent itself, so the message tells it exactly what to do: export that version to a private working copy and open it in Lavish Editor (docmanager's own bundled copy, not fetched from anywhere else) for you to review and edit. Nothing is logged while editing is in progress, only once the session ends and the result is saved as the document's next version. Reverting and deleting versions. While viewing an older version, "Revert to this version" makes it current again - this only changes docmanager's own history, never the real file on disk, and it says so before it fires. Each version chip also has a delete icon for permanently discarding just that one version, with a confirmation step and an outright refusal if it's the document's only remaining version (untrack the whole document instead). Deleting a version never touches the real file on disk or any other version's content. Appearance. A System / Light / Dark control in Settings overrides your OS's own preference just for docmanager's main content area (the sidebar always stays dark). It's a per-browser display choice, not synced anywhere, and applies instantly with no reload. No tracked document's actual HTML content can be edited through it - that job stays with whatever tool you already use. Rendering someone's real HTML safely still takes care, but scripts do need to run: a chart or diagram made with a library like Chart.js, D3, or Mermaid renders nothing at all unless its script executes. So the reading pane loads content inside a sandboxed frame that allows scripts to run but denies it same-origin access to the rest of the app, the same isolation technique Lavish Editor uses for content it doesn't fully trust. A chart in a tracked document renders normally; the script producing it simply has no path to the docmanager UI's own data or API, regardless of what it does. The CLI This is the layer your agent actually touches. It never talks to the store directly; every command is a small HTTP request to the core service running in the background. That indirection is what keeps everything consistent no matter how many places are asking docmanager to do something at once. Two capabilities worth knowing about specifically. First, docmanager now nudges you toward possible duplicates on its own: every time you list your tracked documents, two cheap signals get compared across every pair - a normalized title match, and whether two documents are built from an identical tag structure regardless of their actual text. Either one is enough to flag a pair as a possible duplicate. This is only ever a nudge; docmanager never links two documents on its own, you still decide and run link yourself. Second, docmanager doctor gives you a single command to check whether everything is actually healthy: is git available, is the store a real git repository, does every tracked document's own record actually parse, does its content still exist on disk. Anything that's safe to fix on its own, like a stale internal index or a leftover pointer to a document that's already gone, gets fixed automatically. Anything that might represent real, unrecoverable document loss is only ever reported to you, never touched automatically - the same judgment-call boundary this project draws everywhere else it could destroy real data. How axi-sdk-js works under the hood axi-sdk-js is a small, separate npm package, not written for this project specifically. It exists to give any command-line tool built for agents the same baseline good behavior, without every tool author reinventing it. docmanager-axi depends on it directly and uses it exactly as published, nothing about it is forked or modified. What it actually does for this tool Fast version checks. When an agent runs docmanager --version , a tiny piece of code answers immediately, before the rest of the application even loads. Agents check a tool's version constantly, so this alone keeps every one of those checks close to instant instead of paying the full startup cost each time. Turning plain data into agent-friendly text. Every docmanager command hands back an ordinary JavaScript object. The SDK converts that into a compact text format called TOON before it reaches the terminal, which is easier and cheaper for an agent to read than the equivalent JSON would be. Consistent errors. When something goes wrong, a command throws a small structured error with a short code and a suggestion for what to do next, instead of a raw stack trace. The SDK renders all of these the same way, so an agent learns the pattern once and can rely on it everywhere. A free self-updater. Every tool built this way automatically gets docmanager update and docmanager update --check , with no extra code written for it. Teaching your agent about docmanager at session start. This is what docmanager setup hooks turns on. It quietly registers docmanager with Claude Code, Codex, or OpenCode (whichever you have) so that the very first thing a new agent session sees includes a short summary of what's currently tracked, without you having to explain it every time. There is also a separate, installable Agent Skill for agents whose harness doesn't support that kind of hook, teaching the same commands and behavior on demand instead of automatically. The one real wrinkle The session-hook feature tries to guess a tool's own file layout automatically, and its guess didn't match how this project is actually built, so it silently declined to install anything until it was told explicitly where the real entry point lives. This is mentioned here because it is a good example of the kind of thing that looks fine on paper and only shows up once you actually run it, which is exactly why this whole build leaned so heavily on testing real behavior rather than trusting that the code was correct by inspection. The boundary Everything axi-sdk-js provides stops at "how does the command line behave." The background service, the git-backed storage, and the web page are entirely docmanager's own code, built specifically for this problem, sitting behind that thin, well-behaved command-line shell. A user journey, start to finish 1 You install it and track your first document. npm install -g docmanager-axi docmanager track ./report.html The background service starts on its own. Your document now has a version history of one. 2 You edit the file and forget about it. You open report.html in whatever editor you normally use, change something real, and save. Nothing happens immediately, docmanager isn't watching. The next time you run docmanager status , or just open the web UI, it notices the file changed and records a new version automatically. No prompt, no confirmation. You already told it to track this exact file; there's nothing left to ask you. 3 You realize two files are the same document. Maybe you find an old draft sitting in a different folder, already separately tracked. docmanager link &lt;oldId&gt; &lt;newId&gt; tells docmanager they're the same lineage, and it merges the older file's history in as ancestry of the newer one. This step is always something you decide; docmanager will never guess it on your own. 4 You open and actually read your documents in one place. docmanager ui opens a browser tab. You see every tracked document on the left; clicking one shows its version timeline plus a reading pane rendering the current version's real content, not just metadata about it. Click any earlier entry in the timeline and that older version's content loads into the same pane. Nothing here is editable, it's a place to read, not to work. 5 You set up sync for your other machine. You configure a git remote through the Settings page or docmanager settings set --snapshot-remote &lt;url&gt; , then docmanager snapshot push . Any git URL you already have push access to works: an SSH URL like git@github.com:you/docmanager-snapshot.git , an HTTPS one, or even a local path to a bare repository. The repository has to already exist, empty is fine, docmanager pushes to it rather than creating it. What actually goes into that push is every version of every tracked document's real content, plus each document's full lineage. What never goes into it: where your files live on any particular machine, this setting itself, or any other local configuration. The remote holds your real content, so its privacy is entirely up to how you've set that repository up - docmanager adds no access control of its own on top of it. Rather than only saying so here, the very first push you ever make refuses outright until you run docmanager snapshot push --acknowledge-privacy , which states plainly what's about to leave this machine. It's a one-time confirmation, not a prompt on every push - once acknowledged, every push after that just works. 6 On your other machine, you pull it down. Install docmanager there too, set the same remote, run docmanager snapshot pull . Because it's a brand-new machine with nothing local yet, this clones your entire document history immediately, all of it. The one manual step left is reconnecting each synthetic document to wherever its real files live on this machine, and this works in bulk: point it at the whole folder at once, docmanager track ./reports/ --relink , and every file underneath reconnects to its matching document in one command, not one at a time. docmanager deliberately never guesses this connection on its own. A genuinely new machine often doesn't have git authentication set up yet, which used to just mean a confusing failure here. If your remote is HTTPS, docmanager settings set --snapshot-remote-token &lt;token&gt; covers it - saved locally on this machine only, sent only on the actual push or pull, never part of a snapshot, and never shown back to you once saved. If your remote is SSH, that token does nothing; run docmanager setup ssh instead to check whether this machine's own SSH key is actually working. It only ever reads what's already there and tests the connection - it will never generate a new key for you. If you don't have one yet, that's a real change to your machine, and your agent should only make it with your explicit say-so. Once more than one machine is genuinely in play, docmanager sync is the better default over plain snapshot pull : it does the same fetch-and-merge, but also auto-resolves the two shapes of divergence that come up in ordinary use instead of stopping at a raw git conflict - the same document edited on two machines (both edits are kept, the newer one becomes current), and two machines that each tracked the same document independently before ever syncing (linked automatically, but only when it's unambiguous - anything murkier is reported with the exact command to finish it yourself, never guessed). docmanager sync --dry-run shows you what it would do first if you'd rather preview. 7 You teach your agent about all of this. docmanager setup hooks , run once. From then on, every new Claude Code, Codex, or OpenCode session opens already knowing what's tracked, without you needing to explain your document setup at the start of every conversation. 8 Your agent takes over the routine parts. From here, most of the day-to-day interaction is you telling your agent things in plain language ("track this new draft," "this is a newer version of the report," "what have I got tracked right now") and the agent running the right docmanager commands on your behalf. Repository and CI Repo: github.com/adeeshsharma/docmanager-axi , public. Public visibility and "open for external contributions" are separate things - CONTRIBUTING.md states plainly that PRs and issues from outside contributors aren't currently being reviewed or merged. GitHub gives no way to actually block someone from opening a PR against a public repo, only to decline merging it. CI ( .github/workflows/ci.yml ): a 3-OS matrix job ( ubuntu-latest , windows-latest , macos-latest ) running npm ci --ignore-scripts → build:skill:check → build → test → npm pack --dry-run , on every push and pull request against main . --ignore-scripts is deliberate: better-sqlite3 ships a prebuilt binary for every platform this matrix covers, resolved lazily at require() time with no install step needed - but its own install step still attempts a node-gyp rebuild regardless, which fails hard on windows-latest with no C++ toolchain present. Branch protection on main : requires a pull request, requires the three matrix jobs to pass and be up to date with the base branch before merging. Configured via the GitHub API once the repo went public - branch protection isn't available at all on a private repo without GitHub Pro. .gitattributes : forces LF line endings on checkout ( * text=auto eol=lf ). Without it, a Windows checkout's default CRLF conversion makes the committed SKILL.md byte-different from the freshly-generated comparison in build:skill:check , even though the content is identical - this is exactly what broke that check the first time CI ever ran on Windows. Honest gap, not yet closed: a real end user's plain npm install docmanager-axi on Windows (no --ignore-scripts , since that's not something npm's own install of a dependency does automatically) could still hit the same better-sqlite3 install failure CI's own Windows job hit before being worked around. Worth testing directly on a real Windows machine, or via an npm pack + install-from-tarball dry run, before considering Windows genuinely supported for end users installing the published package - not just for CI. Release process Releases are automated with release-please , following the same pattern already proven out in reactive-axi 's own setup. Every push to main runs .github/workflows/release-please.yml , which keeps one "Release PR" open, proposing the next version and a CHANGELOG.md entry generated from Conventional Commits merged since the last release. Merging that PR tags the release and triggers the same workflow to build, test, and npm publish automatically via npm's Trusted Publishing (OIDC) - no long-lived npm token stored anywhere as a secret. Commit messages matter now. feat: , fix: , feat!: / BREAKING CHANGE: , chore: / docs: / test: for anything that shouldn't bump the version. release-please reads these to decide the next version and the changelog - an unconventional commit message is silently invisible to it, not an error. Full detail lives in RELEASING.md at the repo root, including the one-time bootstrap steps (a package must be manually published once before npm's Trusted Publisher can be configured for it at all - a genuine chicken-and-egg constraint in how OIDC publishing works, not something docmanager-specific). A real lesson from the first automated release, worth knowing before it happens again on some other project: release-please treats a manifest starting value of "0.0.0" as a sentinel meaning "no real version yet," not "start conservatively from zero" - its documented default for a project's very first release under that sentinel is 1.0.0 , regardless of any pre-1.0 bump configuration (which only governs bumps after a real non-sentinel baseline exists). This project's own first release jumped straight from an unpublished 0.0.0 to a published 1.0.0 as a direct result - not a bug, not undone, just not the small cautious bump originally intended. If a future project wants a real, conservative pre-1.0 starting point, the manifest needs to start at something other than the literal "0.0.0" sentinel. npm packaging What ships: package.json 's files field scopes the published tarball to bin , src , dist , skills - full, unminified, readable source, not a built/obfuscated artifact. A public GitHub repo and an installable npm package both mean the same source is visible either way; going private on GitHub would hide commit history and issues, never the distributed code itself. engines.node : ">=22" , corrected from an originally-untested ">=20" - both better-sqlite3 and lavish-axi , direct dependencies, actually require Node 22; Node 20 segfaults the daemon outright the instant it touches the SQLite index, confirmed with a direct repro, not inferred from the dependency's own claim. Provenance: generated automatically by npm as part of the Trusted Publishing OIDC flow now that the repo is public - no --provenance flag needed in the workflow (and passing it explicitly on a private repo errors outright rather than silently skipping, worth remembering if this repo or a future one is ever made private again). prepublishOnly runs the build and full test suite before any publish, manual or automated - a forgotten build step can never ship a package missing its own UI assets, and a broken test suite can never publish at all. Detailed architecture The full build plan lives in ARCHITECTURE.md at the repo root - a living design document, not a frozen spec. This is a condensed technical reference distilled from it, organized for quick lookup rather than narrative reading. Core service lifecycle Singleton via an atomic lock file ( ~/.docmanager/core.lock ), not a check-then-write - an exclusive create means two processes starting at the same instant can't both win. Liveness alone (a PID that's alive) isn't sufficient proof of ownership, since PIDs get reused and an unrelated process could already hold the recorded port - the lock's own /health response is checked against a service identifier too. Fixed port 127.0.0.1:4389 (continuing lavish-axi's 4387, reactive-axi's 4388), not a random one, so an already-open browser tab survives a core restart. Stale-core-after-upgrade detection: every CLI invocation compares the running core's own reported VERSION (from its already-loaded, in-memory code) against the CLI's own freshly-imported version. A mismatch means an upgrade happened since this core last started - it gets sent SIGTERM , waited on to actually exit, and replaced, transparently. This only fires on a real version-string change - editing source locally without a version bump (e.g. between merged PRs, before a real release) leaves an already-running core silently serving old code with no automatic signal. Always docmanager core stop after pulling code changes during local development; don't rely on this mechanism to catch it. core.log capped at 5MB, copy-then-truncate rotation (never rename-then-recreate - the daemon's stdout/stderr stay bound to the file's own descriptor for its whole life, and Node can never reopen process.stdout to a different file at runtime). Idle timeout stops the core automatically after a long period of no activity; an open, connected UI tab counts as activity via its SSE heartbeat and keeps resetting the timer. Storage: three things, kept deliberately separate What Where Synced? Notes Content + metadata ~/.docmanager/store (a real git repo) Yes - this is what push/pull moves Content addressed by hash (the canonical identity of a version); one JSON file per document family holding versions, supersedes links, tags, and synthetic path. Every mutating write, including git operations, goes through a single-writer queue inside the core process. Search index ~/.docmanager/index.db (SQLite + FTS5) No - fully derived Rebuilt from the JSON metadata on startup, after a pull, after any local write. Disposable by design; a rebuild writes to a temp file and swaps it into place so a concurrent query never sees a half-written database. Local machine state ~/.docmanager/local-state.json Never Maps each synthetic path to wherever its source file actually lives on this machine. The synthetic path travels in a snapshot; the real path never does. The two version-capture mechanisms - don't collapse them Automatic, no confirmation: a content change at an already-tracked synthetic path is captured as a new version the moment anything triggers a reconcile (a status check, opening the UI) - there's no ambiguity, the synthetic path is already known to belong to a specific family. ```

The document store this tool uses is a real git repository. If `git` is not installed, docmanager fails with a clear error instead of a raw stack trace. Tell the user git is missing and ask before installing anything on their behalf, never install it silently.

## Core commands

- `docmanager track <path>... [--as <name>] [--relink]` - start tracking one or more files or folders in one call. A folder is tracked recursively for HTML files, skipping vendor/build directories like `node_modules`, `.git`, and `dist`. `--relink` reconnects a file to a document that already exists from a snapshot, and works in bulk on a whole folder at once, the normal way to reconnect an entire pulled snapshot on a new machine.
- `docmanager untrack <id>...` - stop tracking one or more documents. Removes the document's version history from docmanager; never deletes the real file on disk.
- `docmanager link <fromId> <toId>` - declare that `toId` supersedes `fromId`, merging two separately-tracked documents into one version history.
- `docmanager families` / `docmanager families view <id>` - list tracked documents, or show one document's full version history.
- `docmanager families diff <id> <hashA> <hashB>` - show what changed between two versions, computed on normalized content so whitespace/attribute-order noise never shows up as a fake change.
- `docmanager families revert <id> <hash>` - make an older version current again. Changes docmanager's own history only - it never edits the real file on disk. If the real file still holds newer content afterward, the next `status` reports it as behind, exactly like a change pulled in from another machine would.
- `docmanager families delete-version <id> <hash>` - permanently discard one version's own record, not the whole document (`untrack` does that). Heals the history around the deleted version so nothing is left pointing at it; refuses if it's a family's only remaining version, and refuses if a live locally-mapped file still holds that exact content (edit or untrack it first) - otherwise the deleted version would just come right back on the next reconcile.
- `docmanager families rename <id> <newSyntheticPath>` - change a tracked document's synthetic path, keeping its full version history.
- `docmanager families tags <id> [--set "a,b"] [--add <tag>] [--remove <tag>]` - view or change a document's free-form tags; no flags just shows the current ones. Tags are indexed for `search` too.
- `docmanager families export <id> <hash> --to <path>` - write one version's raw content to a real file on disk. Rarely needed directly - `docmanager families lavish` (below) already does this as part of opening a review session.
- `docmanager families lavish <id> <hash>` - export a version to a docmanager-owned working file and open it in Lavish Editor, in one step (see "Editing a version with Lavish Editor" below for the full workflow).
- `docmanager status` - reconciles every tracked file against disk and reports current state, including anything just captured as a new version.
- `docmanager search <query>` - keyword search over tracked documents' paths, titles, and text (current version only). Not semantic search - it won't find a document by meaning alone, only by words actually in it.
- `docmanager settings get` / `set --snapshot-remote <url>` / `set --snapshot-remote-token <token>` - read or set the git remote and, for an HTTPS remote on a machine with no credential helper configured, an access token. `get` never returns the token's real value, only whether one is saved.
- `docmanager snapshot push [--acknowledge-privacy]` / `pull` - sync the document store with the configured remote. Pull clones fresh on a machine that has nothing local yet. The remote's privacy is entirely the user's own responsibility - docmanager adds no access control of its own - so the very first push on a machine refuses until `--acknowledge-privacy` confirms that; a one-time flag, never asked again after.
- `docmanager sync [--dry-run] [--no-auto-link]` - **prefer this over `snapshot pull` whenever more than one machine might be involved.** Does everything `pull` does, plus auto-resolves the two divergence shapes that otherwise force a raw git conflict: the same document edited on two machines (unions both histories, newest edit wins as current), and two machines that each independently tracked the same document before ever syncing (auto-links them, but only when the two histories are completely disjoint and unambiguously ordered by time - anything closer or messier is reported, never guessed). `--dry-run` reports exactly what would happen without changing anything. `--no-auto-link` still detects and reports a path collision but never links it automatically. Falls back to the exact same conflict-and-abort behavior as `snapshot pull` for anything outside those two shapes - see "When a sync hits something it can't resolve automatically" below.
- `docmanager setup ssh` - read-only check of whether SSH auth actually works for an SSH-style remote (checks for an existing key, tests the connection). Never generates a key or writes to `~/.ssh` - if no key exists, generating one is a real change to the user's machine and needs their explicit approval first, the same rule as installing `git`.
- `docmanager ui` - opens the local web interface for reading tracked documents and their version history.
- `docmanager doctor` - checks git availability, store/index health, and document integrity. Auto-repairs what's safe to (a stale internal index, a leftover pointer to an already-gone document); only ever reports anything that could be real data loss, never touches it automatically.
- `docmanager reset --confirm` - permanently deletes the entire `~/.docmanager` directory: every tracked document's full version history, every setting, everything. No undo. Refuses outright without `--confirm`. **Never run this on your own initiative, even when it looks like the obvious fix for a tracking mistake** - the same rule as installing `git` or generating an SSH key. Propose it, explain exactly what it will delete, and only run it after the user says yes, every single time.
- `docmanager gc` - runs git's own housekeeping on the local store to compact history and reclaim disk space, since every version of every document is a git commit forever. Non-destructive (no document data is touched, unlike `reset`) and needs no approval-gating, but is opt-in - only run it when the user asks, not proactively.

## What matters beyond the commands themselves

- A change to an already-tracked file is captured as a new version automatically, the next time anything reads state (a `status` call, or the UI being opened or refocused). No confirmation is needed for this, it is not a guess, the document is already known.
- A newly noticed file is never assumed to be a version of an existing one. If two separately-tracked files turn out to be the same document, that has to be declared explicitly with `link`, never inferred. `docmanager families`/`status` may show a `possibleDuplicates` nudge (a cheap title or structural match between two documents) - it is only ever a suggestion, never acted on automatically. `docmanager sync`'s auto-link is the one narrow, deliberate exception to "never inferred": it only fires on an EXACT synthetic-path match (not a fuzzy title/structural guess like `possibleDuplicates`) between two histories that are provably disjoint (no version in common) and unambiguously ordered by timestamp - never a judgment call, always a mechanical one. There is currently no "unlink" - if two genuinely unrelated documents ever did share a path and got auto-linked, that's not automatically reversible (though nothing is ever deleted in the process, only spliced together) - worth a quick sanity check with the user if a `sync` result ever looks surprising.
- The web UI is for the user themselves to browse and manage documents by hand (reading history, comparing versions, renaming, tagging, bulk untracking). It is not something an agent drives on the user's behalf the way the CLI is.
- A setting changed in the UI takes effect immediately for the CLI too, since both talk to the same background service. There is no need to ask the user to also report a change they already made there.

## When a sync hits something it can't resolve automatically

`docmanager sync`'s JSON result always has three lists: `semanticMerges` (resolved automatically, nothing to do), `autoLinks` (linked automatically, nothing to do), and `unresolved` - entries `sync` found but deliberately didn't act on. What to do next depends on WHY an entry is unresolved:

- If the reason says `not auto-linked (--no-auto-link)` - this is an unambiguous, disjoint collision that was only left alone because that flag was passed. It's safe to run the printed `docmanager link <a> <b>` command directly, the same as any other unambiguous case `sync` would have linked itself.
- If the reason says `ambiguous`, mentions a `3+ way collision`, or `sync` throws `SYNC_CONFLICT` outright - these are genuine judgment calls, not something to guess your way through. **Stop and ask the user** which document's history should actually win, the same discipline this skill already teaches for `link` in general. Make the decision fast and concrete rather than just relaying an error: for an `unresolved` entry, show the user the two families' titles, version counts, and `headCreatedAt` (`docmanager families view <id>` on each id) so they can see at a glance which one is actually older/more complete. For a raw `SYNC_CONFLICT`, first look at what actually happened before proposing anything - `git log --oneline HEAD..origin/main -- families/` inside `~/.docmanager/store` shows the real commits on the other side (a delete, a rename, a version add - each implies a different fix), the same way this exact situation was worked out by hand once already in this project's own history.
- Never resolve an ambiguous or SYNC_CONFLICT case by guessing a direction and running `link` (or hand-editing git) on your own initiative - a wrong guess splices two histories together in a way there's currently no clean way to undo.

## Editing a version with Lavish Editor

The web UI has an "Edit in Lavish" action on any version being viewed, which copies a ready-to-paste prompt for you - or the user may just ask directly to edit a specific tracked document (any version, not necessarily the current one) with Lavish Editor. Either way, this is the workflow:

1. Run `docmanager families lavish <id> <hash>`. This exports that exact version to a docmanager-owned working file and opens it in Lavish Editor, in one step - using docmanager's own bundled `lavish-axi` dependency internally (never `npx`, never a global install, so the version actually running is always the one docmanager was built and tested against). Its output tells you the exact file path and the exact `node <resolved-path> poll <file>` command to run next - **use that command verbatim**, don't substitute your own `lavish-axi`/`npx lavish-axi` invocation, or you may end up polling a different install than the one that opened the session. Keep polling, apply feedback, poll again, same discipline as any other Lavish session.
2. When the review session ends, run `docmanager track <path from step 1> --as <the document's syntheticPath> --relink` followed by `docmanager status`. This is what actually captures the edited result as the document's next version - not step 1, and nothing automatic happens while editing is in progress. Nothing is logged until you explicitly do this.

docmanager has no agent or polling loop of its own - it cannot start or drive a Lavish session by itself. This whole workflow only happens because you, the agent already in this conversation, carry it out end to end.

## How It Works

```
┌────────────────────────────┐
│ docmanager track <path>    │
│ hashes the content, creates│
│ a family + its first       │
│ version                    │
└──────────────┬─────────────┘
               ▼
┌────────────────────────────┐
│ Edit the file, save it. The│
│ next read (a status check, │
│ opening the UI) captures a │
│ new version automatically -│
│ no confirmation needed     │
└──────────────┬─────────────┘
               ▼
┌────────────────────────────┐
│ docmanager ui - read any   │
│ version, diff two of them, │
│ revert, rename, tag        │
└──────────────┬─────────────┘
               ▼
┌────────────────────────────┐
│ docmanager snapshot push - │
│ full history to a git      │
│ remote you control; pull it│
│ down on another machine    │
└────────────────────────────┘
```

- **Tracking** - `docmanager track <path>... [--as <name>] [--relink]` starts tracking one or more files and/or whole folders in one call. A folder is expanded recursively for `.html` files, skipping vendor/build directories (`node_modules`, `.git`, `dist`, and similar) by default, so pointing it at a folder that happens to contain other projects only ever picks up documents that actually belong to the user. One target failing never aborts the rest of a batch.
- **Automatic version capture** - a change to an already-tracked file becomes a new version the next time anything reads state (`docmanager status`, opening the UI). No live filesystem watcher in this version - reconciliation is triggered by a read, not continuous.
- **Never guesses a link** - `docmanager families`/`status` may flag a `possibleDuplicates` entry when two separately-tracked documents share a normalized title or near-identical structure. It's a cheap heuristic nudge, never acted on automatically - review it and run `docmanager link <fromId> <toId>` yourself if it really is the same document.
- **Diff, revert, delete a version** - `docmanager families diff <id> <hashA> <hashB>` (a line diff on normalized content, so whitespace-only differences never show up as fake changes), `docmanager families revert <id> <hash>` (moves the current version back; never edits the real file on disk), `docmanager families delete-version <id> <hash>` (permanently discards one version's record, healing the history around it - refuses on a document's only remaining version, and refuses if a live locally-mapped file still holds that exact content, since the next reconcile would just bring it right back).
- **Rename and tag** - `docmanager families rename <id> <newPath>` changes a document's synthetic path without losing any history. `docmanager families tags <id> [--set/--add/--remove]` attaches free-form labels, indexed for search too.
- **Edit a version with Lavish Editor** - the UI's "Edit in Lavish" button copies a ready-to-paste message for your agent, naming the exact version you're looking at. docmanager doesn't run the editing session itself (it has no agent loop of its own) - the agent does: `docmanager families lavish <id> <hash>` exports that version to a docmanager-owned working file and opens it in Lavish Editor in one step, using docmanager's own bundled `lavish-axi` dependency directly (never `npx`, never a global install), then `docmanager track <path> --as <name> --relink` + `docmanager status` capture the result as the next version once the review session ends - nothing is logged before that.
- **Keyword search** - `docmanager search <query>` finds a tracked document by the words actually in its path, title, or text (including tags). Not semantic search - it won't find a document by meaning alone.
- **Cross-machine sync** - `docmanager settings set --snapshot-remote <git-url>` then `docmanager snapshot push`/`pull`. A pull on a brand-new machine reconstructs the full document and version history immediately; the one manual step is reconnecting a synthetic path to a live file with `track --as <path> --relink`, since the tool never guesses that a file on a new machine is the same as one from a snapshot. `docmanager sync` (preferred over plain `pull` whenever more than one machine may be involved) additionally auto-resolves the two most common divergence shapes on its own - the same document edited on two machines, and two machines that independently tracked the same document before ever syncing - falling back to the same clean, zero-data-loss conflict abort as `pull` for anything less mechanical (`--dry-run` to preview, `--no-auto-link` to report a path collision without linking it). The remote's own privacy is entirely your responsibility - docmanager adds no access control on top of it - so the very first push refuses until you run `docmanager snapshot push --acknowledge-privacy`; a one-time confirmation, never asked again after.
- **Fresh-machine auth** - an HTTPS remote can use an access token (`docmanager settings set --snapshot-remote-token <token>`, local-only, never part of a snapshot); an SSH remote uses this machine's own key, checked read-only with `docmanager setup ssh` (never generates a key on its own - the same approval-gating rule as installing `git`).
- **The background service** - the first `docmanager` command starts a small background process automatically; it stops itself after a long period of no activity, or immediately with `docmanager core stop`. After an upgrade, it also detects that it's running older code than what's actually installed and restarts itself transparently the next time it's needed.
- **`docmanager doctor`** - checks git/store/index/local-state health, auto-repairing what's provably safe and reporting the rest for a human to decide.
- **`docmanager reset --confirm`** - the safe, supported way to delete everything and start fresh, instead of manually removing `~/.docmanager`. Irreversible, refuses without `--confirm`, and an agent must never run it on its own initiative - the same rule as installing `git` or generating an SSH key.
- **`docmanager gc`** - runs `git gc` on the local store to compact its history and reclaim disk space, since every version of every tracked document is a git commit forever. Non-destructive (document data is untouched) and opt-in - never run automatically.

## CLI Reference

| Command | Does |
|---|---|
| `docmanager` | Show current state: core status, tracked document count |
| `docmanager track <path>... [--as <name>] [--relink]` | Start tracking one or more files and/or folders |
| `docmanager untrack <id>...` | Stop tracking one or more documents (does not delete the real files) |
| `docmanager link <fromId> <toId>` | Declare that `toId` supersedes `fromId` |

| `docmanager families delete-version <id> <hash>` | Permanently discard one version's record |
| `docmanager families export <id> <hash> --to <path>` | Write one version's raw content to a file |
| `docmanager families lavish <id> <hash>` | Export a version and open it in Lavish Editor, in one step |
| `docmanager families rename <id> <newSyntheticPath>` | Change a document's synthetic path, keeping its full history |
| `docmanager families tags <id> [--set "a,b"] [--add <tag>] [--remove <tag>]` | View or change a document's tags |

## What this project is

`docmanager-axi` — helps a user manage the sprawl of HTML documents on their machine: tracking which files are versions of the same document, building a version lineage the way git tracks commits, and letting the workspace snapshot to a git remote so document history follows the user across machines. It manages and versions documents; it does not edit them (that's [lavish-axi](https://github.com/kunchenguid/lavish-axi)'s job). Full rationale in `memory-bank/projectbrief.md` and `memory-bank/productContext.md`.

## Things to know when editing

- **The suggestion-vs-automatic version-capture distinction is load-bearing.** A content change at an *already-tracked* synthetic path is captured as a new version automatically, no confirmation. A *newly noticed, previously untracked* file that merely resembles an existing family is only ever suggested, never auto-linked. These are two different mechanisms — don't collapse them. See `memory-bank/systemPatterns.md`.
- **v1 has no passive file-watching.** Reconciliation is triggered by a read — a CLI call, or the UI loading/regaining focus — not a background watcher. Don't build one for v1; it's explicitly phase 2.
- **Any autonomous install action (e.g. installing `git` if missing) requires explicit user approval first.** The README's setup instructions are written for an agent to act on, but never silently.
- **Generating an SSH key (`ssh-keygen`) is the same class of action and needs the same explicit, in-the-moment approval every time - never a standing permission.** `docmanager setup ssh` is deliberately read-only: it checks for existing keys and tests connectivity, but never writes to `~/.ssh`. If it reports no key found, that is information for you to act on with the user's explicit go-ahead, not something `docmanager` or an agent should do on its own initiative.
- **`docmanager reset --confirm` is the same class of action too, and needs the same rule.** It permanently deletes the entire `~/.docmanager` directory - every tracked document's full version history, every setting, everything - with no undo. An agent must never run this on its own initiative, even when it looks like the obvious fix for a tracking mistake (a whole-folder tracked by accident, a corrupted-looking store). Propose it, explain exactly what it will delete, and only run it after the user says yes - every time, not a standing permission, the same discipline already applied to `git` installation and SSH key generation above.
- **The core service is a singleton, enforced via an atomic exclusive-create lock file**, not a check-then-write — see `memory-bank/systemPatterns.md` for why the naive version races, and why PID liveness alone isn't sufficient proof of ownership.
- **Loopback binding is not enough on its own for the core's HTTP API.** It must check the `Origin` header, since a browser tab on the same machine can otherwise reach it too (the DNS-rebinding class of attack). See `ARCHITECTURE.md` section 3.3.
