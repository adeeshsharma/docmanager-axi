docmanager-axi is a published, actively-used npm package (currently v1.5.0) that helps a user track HTML documents as version-lineage "families," the way git tracks commits - content-addressed, git-backed storage, a derived SQLite index, a CLI built on axi-sdk-js, and a local web UI whose reading pane is the primary way a user actually reads a tracked document. It ships as a single npm package with no bundler, syncs across machines via a user-provided git remote, and is designed to be driven primarily by a coding agent shelling out to its CLI.

Major capabilities beyond the original v1 scope, in build order: folders (a nested, synthetic-path-independent organization hierarchy, released in 1.2.0), cross-document link resolution (tracking a document also tracks whatever HTML it links to, and an <a href> between two tracked documents actually resolves and navigates inside the reading pane instead of being dead), per-version text highlights (select text in the reading pane, mark it in one of 4 colors), and, as of 2026-09-13, cascading highlights - capturing a new version now automatically carries a version's highlights forward onto it, re-anchored by exact substring search in the new version's own flattened visible text (extractFlattenedVisibleText() in html-normalize.js), with a highlight whose exact text was edited away dropped rather than guessed at. This directly reverses the original 2026-08-31 per-version-highlights design's explicit 'scoped to the exact version, never inherited by a newer version' decision - that was a deliberate v1 scoping choice, not a technical constraint, and the user asked for it reversed; see decisions.md. The change lives entirely in store.js (recordVersionIfChanged) plus the new html-normalize.js export - no server.js or UI change was needed, since handleContent() already reads a version's highlights straight off the store record.

Architectural work in this project now consistently follows brainstorm -> written spec -> written implementation plan -> TDD task-by-task build -> manual Playwright verification for anything UI-facing, always landing via a feature branch + PR, never merged by the agent itself. Manual browser verification specifically has caught real, non-hypothetical bugs multiple times now (not just this round) - it is treated as a required step for UI-touching work, not an optional nicety, and a temporary Playwright install is always fully removed afterward (confirmed via a clean git status on package.json/package-lock.json) rather than left as a standing dependency. The cascading-highlights change above was backend-only (no UI surface changed), so it followed brainstorm -> short in-chat design -> TDD build, without a written spec/plan doc or Playwright verification - proportional process for a bounded change, not a shortcut on a genuinely architectural one.

This project's own memory lives in Memory Intel (.memoryintel/), migrated off a hand-maintained memory-bank/ folder. A real reliability gap found during that migration (nothing forced committing .memoryintel/'s own changes, especially from a worktree) was fixed upstream in the separate memoryintel package (now memoryintel doctor, released alongside a fix to instructions.md itself never spelling out the exact TOON update-plan syntax an agent needs - both real, user-facing gaps found and fixed in that sibling project this same era, not merely in docmanager-axi).
