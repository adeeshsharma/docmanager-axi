## Confirmed findings from the core service skeleton (phase 1, step 2)

**A real bug found and fixed during testing, not by code review alone**: `ensureCoreRunning()`'s retry loop cleared a stale lock (`clearLock()`) and then `continue`d to the next iteration, which re-reads the lock file — but that file had just been deleted, so it always read as `null`. The code that spawns the daemon with a preferred port was computing `staleLockPort` from that now-null `lock`, so a crash-recovery restart always fell through to a random port (`0`) instead of the doc's stated behavior of "tries to reacquire the same port on restart." Caught by an actual end-to-end test (`kill -9` the daemon, restart, compare ports), not by reading the code — the bug was invisible without running it. Fixed by hoisting a `lastKnownPort` variable outside the loop, set at the moment a stale lock is detected (before it's cleared), and used when spawning. Re-verified: a killed daemon now correctly restarts on the exact same port.

**Verified for real, end to end** (not just "the code looks right"):
- `core status` with nothing running reports `not running`; `core start` spawns a detached daemon and returns real `{pid, port}`; a second `core start` reuses the same process (`ps aux` shows exactly one `daemon.js`), confirmed even under **5 concurrent `core start` invocations** launched in parallel — all five returned the same pid/port, still exactly one process. This is the exclusive-lock-file-create race-safety design from `ARCHITECTURE.md`/`systemPatterns.md`, proven under real concurrent load, not just reasoned about.
- Crash recovery: `kill -9` on the daemon leaves a stale lock file; `core status` correctly reports `not running` (PID-liveness check catches it); `core start` clears the stale lock and restarts, reusing the same port (after the fix above), still exactly one process afterward.
- `core stop` sends `SIGTERM`, clears the lock, and a repeated `core stop` is a genuine no-op (`"already stopped"`, matching the AXI idempotent-mutation convention) rather than an error.
- `GET /health` returns `{service, version, pid}`; a request with a mismatched `Origin` header gets `403`; a request with the correct own-origin `Origin` header gets `200`; an unknown route gets a structured `404` JSON body, not a raw Node error page.
- `~/.docmanager` is created at `0700` (confirmed via `stat`), matching the "holds document content, user-only" requirement.
- `~/.docmanager/core.log` is wired (daemon's stdout/stderr redirected to it via the spawn call's `stdio` option) but stayed empty throughout testing, since nothing the daemon does today logs anything or crashes internally — expected, not a gap; it exists for when phase 2+ gives the daemon something worth logging.

**Not yet exercised**: Windows/Ubuntu detached-spawn and process-kill semantics — this was all verified on macOS only (the dev machine). Still an open, acknowledged risk per `systemPatterns.md`'s "known architectural risks" list, not newly discovered here.

## Confirmed findings from the storage layer (phase 2)

**A real bug caught before it shipped, not after**: the first draft of `store.js` wrapped every mutating operation (`initStore`, `createFamily`, `recordVersionIfChanged`) in the single-writer `serialize()` queue, and had `createFamily`/`recordVersionIfChanged` call `initStore()` internally to guarantee the store exists first. Tracing it through by hand: `serialize()` reassigns the module-level `writeQueue` to a new promise chained after the *current* call's own result **before** that call's body actually runs (the reassignment happens synchronously when `serialize()` is invoked, the body runs later as a microtask). So a nested `serialize()` call made from inside an already-serialized function reads a `writeQueue` that now depends on the outer call finishing - and the outer call is `await`ing the inner one - a genuine deadlock (not a crash, a permanently-pending promise). Fixed by never nesting `serialize()` calls: an unlocked `ensureStoreExistsUnlocked()` helper does the raw work, and every public mutating function calls `serialize()` exactly once at its own top level, calling the unlocked helper from inside that single callback. Caught by re-reading the control flow before ever running it - worth remembering as a class of bug (a promise-chain "queue" pattern silently deadlocks under any nesting) rather than a one-off.

**A second real bug, caught by testing `rebuildIndex()` specifically**: the SQLite index module cached an open `Database` handle across calls (`dbHandle`, opened lazily). `rebuildIndex()` writes a fresh index to a temp file and `renameSync`s it over the real path - but on POSIX, an already-open file descriptor keeps reading the *old* inode's content even after the path it was opened from gets renamed over. A cached handle would have silently kept serving stale query results forever after any rebuild. Fixed by having `rebuildIndex()` close and null out the cached handle before doing the temp-write-then-rename, so the next query reopens fresh from the new file. This is exactly the kind of bug that "looks correct" in a code read and only shows up once you actually rebuild the index while holding an open handle and query again - which the test script below does, and which is why it was caught now rather than in phase 4 when the API layer starts holding long-lived handles.

**Verified for real, end to end** (a throwaway test script exercising `store.js`/`index.js` directly, deleted after use - `docmanager track`/`link` CLI commands don't exist until phase 3, so this was the only way to test the storage layer in isolation):
- `initStore()` creates the store directory, `git init`s it, writes `.gitattributes` (`* -text`, confirmed present), and makes an initial commit.
- `createFamily()` writes content by hash, writes the family JSON, commits. A second `createFamily()` at the **same synthetic path** throws `FAMILY_PATH_EXISTS` - confirmed this is a storage-layer invariant, not just a CLI-level check.
- `recordVersionIfChanged()` with **unchanged** content is a real no-op: `changed: false`, version count stays at 1, no new commit. With **changed** content: `changed: true`, a second version entry appears with `supersedes` pointing at the prior head, a new commit is made, and `headVersion` advances. This is the "automatic, no-confirmation capture at an already-tracked path" mechanism from `systemPatterns.md`, now proven working, not just designed.
- **Content dedup across families confirmed**: writing byte-identical content under a second, different synthetic path reuses the exact same content hash/file rather than duplicating it - matches the documented "deduplicates the blob but never merges families" rule.
- **Concurrency stress test**: 5 `createFamily()` calls fired via `Promise.all` (not sequential awaits) all completed successfully with 5 distinct families and no git corruption - proves the single-writer queue actually serializes real git operations under concurrent load, not just in the happy-path single-caller case.
- `readContent()` round-trips exactly byte-for-byte against what was written.
- `rebuildIndex()` + `listFamiliesFromIndex()`/`getFamilyFromIndex()` return data that matches the on-disk JSON exactly (family count, version count, head version) after all of the above operations, including after the concurrency test.
- `GitUnavailableError`/`assertGitAvailable()` verified directly: with `PATH` restricted to a directory containing only a `node` symlink (no `git`), `assertGitAvailable()` throws the structured error with `code: "GIT_UNAVAILABLE"` and a message pointing at README setup instructions, exactly as designed in `ARCHITECTURE.md`/`systemPatterns.md`. (Once `checked` is set `true` for a real git install, it's cached for the process lifetime - deliberate, avoids re-shelling-out to `git --version` before every single git command.)

**Schema note for later phases**: a family's `versions` map uses `supersedes: <hash-or-null>` per version (parent-pointer style, like git commits) rather than assuming a strictly linear array - this leaves room for a non-linear version graph later without a schema migration, even though v1's CLI only ever extends the current `headVersion` linearly. `title`/`syntheticPath` are mutable fields on the family record; `id` (a UUID, not derived from path or content) is the stable identity version links and the future UI's version-graph view should key on.

## Confirmed findings from tracking and versioning (phase 3)

**A real architectural correction made before writing any code**: `ARCHITECTURE.md` states CLI commands are thin HTTP clients to the core, never touching storage directly. Re-deriving *why* while starting phase 3 surfaced a concrete correctness reason, not just doc-fidelity: `store.js`'s single-writer queue (`serialize()`) only serializes writes *within one process's lifetime*. If CLI command handlers called `store.js` directly, each CLI invocation is a fresh Node process with its own empty queue, and the serialization guarantee silently stops protecting concurrent CLI/UI operations across processes. So phase 3 added real HTTP routes to `src/core/server.js` (`GET /families`, `GET /families/:id`, `POST /documents/track`, `POST /link`) now, rather than deferring API-surface work to phase 4 as originally planned - the CLI cannot be correct without it. `src/cli/client.js` is the HTTP client layer (surfaces the server's real `error`/`code`, not just the bare HTTP status - a documented gotcha in reactive-axi's own history that's now avoided from the start here).

**Three real bugs found only by running the CLI end to end, not by reading the code:**
1. **`git init` was never actually called before the first real `track`.** `createFamily`/`recordVersionIfChanged`/`mergeFamilies` all called an "ensure store exists" helper that only created directories - the actual `git init` + first commit lived solely inside the separately-exported `initStore()`, which nothing calls automatically. First real `docmanager track` failed outright (`git add -A failed: not a git repository`) after already writing the family JSON and content blob to disk - a genuine partial-state bug, not just a clean failure. Fixed by merging directory-creation and `git init` into one async `ensureStoreReadyUnlocked()`, called by every mutating store function. Re-verified: a fresh `track` on a clean `~/.docmanager` now works end to end with a correct 2-commit git history (`Initialize store`, `Track /path`).
2. **HTML "normalization" wasn't actually normalizing whitespace.** `parse5`'s parse-then-serialize round trip preserves whitespace exactly - it fixes up malformed structure but does not collapse indentation/newlines added purely for source formatting between tags. A whitespace-only edit (adding newlines/indentation to an already-tracked file) incorrectly triggered a real new version capture in the first end-to-end reconciliation test - directly contradicting the "collapsed insignificant whitespace" requirement in `ARCHITECTURE.md` section 3.4 and the noise-avoidance goal discussed with the user. Fixed by adding an explicit whitespace-normalization pass in `html-normalize.js`: text nodes that are purely whitespace are dropped entirely (safe always - never meaningfully rendered), text nodes with real content have internal whitespace runs collapsed to a single space but keep their leading/trailing whitespace (preserves inline-adjacency significance, e.g. `<span>a</span> <span>b</span>` staying two words). Re-verified in isolation first (a direct `normalizeHtml` comparison), then through the real CLI: a whitespace-only edit now correctly leaves `versionCount` unchanged; a real content edit still correctly captures a new version.
3. **Tracking an already-tracked path was wired as a thrown error (`ALREADY_TRACKED`), contradicting the AXI idempotent-mutation principle this project's own `systemPatterns.md`/`AGENTS.md` already documents** ("closing an already-closed thing is a no-op, not an error"). Caught before shipping, while re-reading the design rather than by a failing test - re-tracking the same path is exactly this case: the desired end state is already true. Fixed: `track.js`'s `trackPath()` now returns `{ family, alreadyTracked: true }` instead of throwing; the CLI reports it as a successful no-op (`note: "already tracked, no changes made"`, exit 0) rather than an error.

**Verified for real, end to end, through the actual `docmanager` binary** (not the storage layer in isolation this time - `docmanager core start`/`track`/`link`/`families`/`status` all exercised as real separate CLI invocations against a real running daemon):
- `track` on a new file creates a family and reports it; re-running the identical `track` is a genuine no-op (exit 0, `note` field, no new commit).
- A whitespace-only edit to a tracked file leaves `versionCount` at 1; a real content edit advances it to 2, both observed via `docmanager status`'s reconciliation.
- `link <fromId> <toId>` correctly merges two independently-tracked families into one: the older family's version chain is spliced in as ancestry, the older family record disappears from `families` (down from 2 tracked to 1), and `families view` shows a correct 3-entry `supersedes` chain with exactly one `current: true` entry.
- A tracked file deleted from disk is reported as `missingOnDisk` by `status`, not a crash or a swallowed silence - exit code stays 0 (this is informational state, not a command failure).
- Every planned error path produces the right `AxiError` code and exit code: `FAMILY_NOT_FOUND`/`SAME_FAMILY`/`FILE_NOT_FOUND` all exit 1 with an actionable suggestion; an unknown flag exits 2 (`VALIDATION_ERROR`) with the valid-flags list inlined, matching the AXI "fail loud, self-correcting in one turn" principle.
- **5 concurrent `docmanager track` calls launched as 5 real, separate OS processes** (not concurrent promises within one process, which phase 2's test already covered) all succeeded with 6 correctly distinct families and a perfectly linear, uncorrupted git history in the store - direct proof the CLI-as-thin-HTTP-client architecture actually delivers the cross-process write-serialization guarantee it was specifically built for in point 1 above.

**Dependency added**: `parse5` (WHATWG HTML parsing algorithm - the same one browsers use, chosen specifically for real-world tolerance of not-strictly-well-formed HTML, per the risk already flagged in `systemPatterns.md`).

## Confirmed findings from the UI (phase 4)

**Scope decision made explicitly, not left implicit**: `ARCHITECTURE.md` describes the family view as a version "graph" (DAG). In practice, nothing in this codebase ever creates a branch - `recordVersionIfChanged` always extends the current head linearly, and `mergeFamilies` always splices one whole chain in as ancestry of another, never creating two children of one version. So v1's family data is always a linear chain, and the UI renders it as a timeline (a single ordered list with a connecting line), not a general graph-layout algorithm. Building a generic DAG renderer for a shape the data model can't currently produce would be premature; revisit if a future version of `mergeFamilies` (or a real UI-driven branch action) ever produces non-linear history.

**No frontend framework, no build step.** Chosen deliberately, not just left at the doc's stated default: plain HTML/CSS/vanilla JS served directly by the core (`src/ui/index.html`/`app.js`/`style.css`), matching the "keep the npm package small" goal from `ARCHITECTURE.md` section 5. `server.js`'s static file handler checks `dist/ui` first, falling back to `src/ui` - so packaging (phase 7) only needs to copy files into `dist/ui`, no bundler dependency required at all for this scope.

**A real cross-client inconsistency bug, caught only by comparing the raw API response against what the UI's JS actually expected, not by testing either client alone**: `GET /families/:id`'s version rows come straight from SQLite via `getFamilyFromIndex` and never carried a `current` field - the CLI's `families view` command happened to look correct anyway because it was separately, redundantly computing `current: v.hash === family.headVersion` itself on the client side. `app.js` was written assuming the API already provided `current` (a reasonable assumption - the CLI's own output style suggested it), so the UI would have silently rendered every version as "not current," with the current-version badge and highlight dot never appearing, no error, nothing visibly broken to notice. Caught by explicitly diffing the raw JSON response's keys against what `app.js` reads. Fixed at the actual source: `getFamilyFromIndex` now computes `current` once, server-side, so the API is self-describing; the CLI's own duplicate computation was then deleted rather than left as harmless-but-redundant, since duplicated derivations are exactly what let this drift happen in the first place.

**Verified for real, through actual HTTP requests** (a real running core, `curl`, not a real browser session - see "not yet exercised" below for why): static file serving (`/`, `/app.js`, `/style.css` all correct content-types; an unknown static path 404s cleanly, no raw filesystem error text leaked); `GET`/`PUT /settings` round-trip correctly and reject an unknown setting key with `UNKNOWN_SETTING`; the Origin-header check applies uniformly to every new route, not just the original `/health`; `GET /events` establishes a real SSE stream and a `track` call while connected delivers a real `families-changed` event over it, confirmed by capturing the actual stream output; `GET /families`/`GET /families/:id` response shapes were directly diffed against what `app.js` reads field-by-field (this is what caught the `current` bug above); `app.js` passes `node --check` (syntax-valid).

## Confirmed findings from snapshot and sync (phase 5)

**A foundational fix made before any sync testing could even be meaningful**: `store.js`'s `git init` never pinned a branch name. Two machines' git installs can have different `init.defaultBranch` config (this is a real, common source of drift, not theoretical), which would have meant two machines' stores could genuinely be on different branch names and never sync at all. Fixed by changing init to `git init -b main` explicitly, so every machine's store is on the same branch regardless of local git config.

**`DOCMANAGER_HOME` env override added** (`src/core/paths.js`) - not just a nice-to-have, this was the only way to actually test cross-machine sync for real: two independent `docmanager` instances, each with their own home directory, talking to a shared local bare git remote, genuinely simulate two machines on one dev box.

**A real "relink" mechanism had to be built that didn't exist before this phase**: `ARCHITECTURE.md` promises relinking a synthetic path to a live file on a new machine as "a separate, explicit step," but nothing implemented that step - `track.js` only knew how to create a new family or recognize an already-locally-mapped path. Running the actual two-machine test immediately hit this: after a fresh clone, tracking the same document at its real path on the new machine hit `FAMILY_PATH_EXISTS` with no way forward. Added `track --relink`: if the synthetic path already belongs to a family with no local-state mapping yet, `--relink` connects this real path to that existing family without creating a duplicate or requiring the content to match exactly at that instant - the next reconcile naturally captures any drift, reusing existing machinery instead of adding a special case.

**The most serious bug found in this entire build, caught only by a genuine two-machine end-to-end test**: after Machine A pushed, Machine B cloned, relinked, edited, and pushed back, Machine A pulled B's change successfully (a clean git fast-forward, no conflict) - but the very next read on A silently corrupted the family's history. Root cause: A's own `local-state.json` still pointed at A's original, never-edited copy of the file. `reconcile()` compared that stale local file's hash against the family's (now newer, pulled-in) head version, saw a difference, and - having no concept of "this hash is already known, just not the head" - recorded A's *old* content as a *brand new* version, flipping `headVersion` back to old content and pointing the real newest version's `supersedes` chain backwards. This silently rewrote the family's lineage to claim the old content was newest, with no error, no warning - the exact kind of bug that's invisible until you build the full loop and watch it happen. Root-caused by literally reading the git history apart from the JSON diff (nothing in the merge itself was wrong; the corruption was reconcile()'s own read-then-write reasoning, applied one command *after* the pull). Fixed in `reconcile.js`: before treating a difference from the head as a new edit, check whether the current file's raw hash already exists ANYWHERE in the family's known version history. If it does (and isn't the head), the live file is simply behind - a `behind-head` status, purely informational, never a write. Re-verified with the exact same two-machine sequence that first exposed it: `headVersion` now correctly stays on B's real edit after A's pull, history stays intact and correctly ordered, and `docmanager status` on A now reports `behindHead: ["/report"]` instead of silently corrupting anything.

**Verified for real, end to end, with a genuine two-"machine" simulation** (`DOCMANAGER_HOME`-isolated instances A and B, a real local bare git remote, not mocks): A tracks and pushes; B (fresh, no local store) pulls and correctly **clones** rather than assuming a repo exists; B's naive re-track without `--relink` correctly errors with an actionable suggestion; `--relink` correctly connects B's real path to the existing family with the same family id preserved across machines; B edits, reconciles, and pushes; A pulls and correctly fast-forward-merges B's change; the reconciliation-corruption bug above was found, root-caused, and fixed in this exact sequence; a genuine conflict (both A and B independently edit before either syncs, B pushes first, A's push is correctly rejected as non-fast-forward with `PUSH_REJECTED`, A's pull correctly detects the real conflict, aborts the merge cleanly - confirmed via `git status --short` showing a clean working tree afterward - and A's own local history is verified fully intact and uncorrupted, still showing A's own unpushed version at head, nothing lost).

## Confirmed findings from session integration (phase 6)

**A real gotcha caught by reading `axi-sdk-js`'s actual source before wiring this up, not by trial and error**: `installSessionStartHooks()` auto-infers a marker/entrypoint shape from either a `dist/bin/<name>.js` path or a dot-free bare filename. This project's real entrypoint is `bin/docmanager.js` - no `dist/` build step for the CLI itself (only the UI assets build into `dist/ui`; see phase 4) - which matches neither inference pattern. Passing `marker`/`binaryNames` alone was not enough either: the install still silently no-opped, because `shouldInstallHooksForNodeAxiExecPath`'s safety policy separately checks the execPath against `distEntrypoints` (defaulting to `["dist/bin/<marker>.js"]`) before agreeing to install anything at all, and refuses installation for an entrypoint shape it doesn't recognize as safe. Fixed by explicitly passing `distEntrypoints: ["bin/docmanager.js"]`, matching this project's real (non-`dist/bin`) layout.

**Verified without touching the real, global `~/.claude`/`~/.codex` config as a side effect of testing.** `installSessionStartHooks()` writes to global, cross-session state - the moment it's installed for real, every future Claude Code/Codex/OpenCode session (including ones unrelated to this project) starts running `docmanager` for ambient context. Since the SDK itself exposes a `homeDir` override (clearly meant for exactly this kind of testing), the whole mechanism was verified against a scratch home directory instead of the real one: `docmanager setup hooks`'s underlying call correctly wrote a `SessionStart` hook into a fake `~/.claude/settings.json` and `~/.codex/hooks.json`, set `[features] hooks = true` in a fake `~/.codex/config.toml`, and generated a working OpenCode ambient-context plugin file. The installed hook command was then actually executed directly (exactly as a real SessionStart hook would invoke it) and confirmed to produce sensible TOON ambient-context output - the same home view content `docmanager`'s bare invocation already produces. Running the install twice confirmed idempotency (still exactly one hook entry, not a duplicate). The actual `docmanager setup hooks` CLI command (which always targets the real home directory, as it should for real use) was verified only for its help text and error path (unknown subcommand → `VALIDATION_ERROR`, exit 2) - never actually run for real, deliberately, so this session's own global Claude Code config stays untouched by its own test process.

## Confirmed findings from batch/folder tracking and the UI's track form (post-v1, driven by design review feedback)

Two real product corrections came out of the user reviewing `docs/understanding-docmanager-axi.html`, not from new planning: (1) the UI's core purpose is reading tracked documents, not just browsing version metadata (the reading pane itself, with a sandboxed-but-scripts-enabled iframe, is designed and written up but still not built - see the UI review discussion in conversation history, not this file, for the full design); (2) `track` needed to support folders and multiple paths in one call, both from the CLI and from a new UI form, not just a single file.

**A real technical constraint decided the UI's tracking affordance, not a preference**: a browser cannot expose the real absolute path of a file picked via `<input type="file">`, drag-and-drop, or a native file dialog triggered from a web page - this is a deliberate, unavoidable browser security boundary, not a gap to work around. Since `track` fundamentally needs a real path to reconcile against for future edits, "upload a file" was ruled out entirely in favor of a plain path-entry field (a multi-line textarea, one path per line) that calls the exact same batched `/documents/track` endpoint the CLI uses.

**Folder tracking required a real design decision on synthetic-path collisions**: the existing single-file default (`syntheticPath = basename without extension`) would collide the moment two same-named files in different subfolders got tracked in one folder walk (e.g. `reports/q3.html` and `notes/q3.html` both wanting `/q3`). Fixed by deriving a discovered file's synthetic path from its location relative to the tracked folder's root (`syntheticPathForDiscoveredFile`), not just its filename - confirmed directly with a real fixture (`reports/q3.html`, `notes/q3.html`, `notes/sub/deep.html` under one folder) producing `/reports/q3`, `/notes/q3`, `/notes/sub/deep` with zero collisions, not assumed correct from the code alone.

**The wire format for `POST /documents/track` was redesigned, not extended**: `{path, as, relink}` → `{paths: [...], as, relink}`, returning `{results: [...], summary}` instead of a single family. Since nothing is published and there are no external consumers yet, this was a clean redesign, not a versioned/backwards-compatible change - consistent with this project's own stated principle against backwards-compatibility shims when the code can just be changed directly.

**One failure never aborts a batch**: each target (whether a literal input path or a file discovered inside a tracked folder) gets tried and recorded independently. Verified directly: a batch of one valid new file plus one nonexistent path correctly tracked the valid one and reported the missing one as a per-item error, not a whole-command failure.

**Symlink-loop protection was added to the recursive folder walk on the reasoning that it's cheap insurance for a rare but real risk**, not because a loop was actually observed - `collectHtmlFiles` tracks visited real (symlink-resolved) directories and refuses to re-walk one already seen.

**Verified for real, end to end, including the standout new capability**: track a whole folder in one command (4 files found, correct relative synthetic paths, `readme.txt` correctly excluded); re-tracking the same already-tracked folder is fully idempotent (all report `already-tracked`, zero new commits implied); `--as` combined with a folder or multiple paths correctly rejects with `AS_REQUIRES_SINGLE_FILE`; an empty folder reports `no-html-files-found` rather than silently doing nothing; and, using the same two-machine `DOCMANAGER_HOME` simulation from phase 5, a whole folder tracked and pushed on machine A was **bulk-relinked on machine B in one command** after a fresh clone - the individual per-file `FAMILY_PATH_EXISTS` errors appeared correctly first (without `--relink`), then all 5 relinked cleanly together with `--relink`. The UI's new track form was verified by calling the exact same endpoint it calls via `curl` (matching the same "test the real API shape the client depends on" discipline used throughout this project) and by confirming the built `dist/ui` page actually contains the new form elements after a rebuild. A full CLI regression pass (`--version`, `core start/stop`, `track`, `families`, `link`, `status`, `settings get`) confirmed nothing else broke from the wire-format change.

## Confirmed findings from the reading pane and UI visual redesign (post-v1, second review round)

**`GET /content/:hash` needed its own input-validation discipline, not just reuse of `readContent`.** The hash comes straight from the URL, and `store.js`'s `readContent()` builds a filesystem path from it with zero validation of its own. A strict format check (`/^[0-9a-f]{64}$/`, real sha256 output and nothing else) was added at the route boundary specifically because that is the actual untrusted-input boundary - verified directly with a real path-traversal attempt (`/content/..%2f..%2f..%2fetc%2fpasswd`), which correctly 400s before ever reaching the filesystem, not just returns a 404 that happens to look safe.

**The route had to be handled outside the JSON-dispatch table**, the same way `/events` already was - it serves raw HTML bytes for the iframe to load, not a JSON body, so it needed its own response-writing path rather than fitting the existing `{status, body}` route contract.

**The sandbox attribute was verified in the actual built output, not just the source file**: `grep`'d the built `dist/ui/index.html` for the literal `sandbox="..."` string and confirmed it reads exactly `sandbox="allow-scripts"` - no `allow-same-origin`, no `allow-top-navigation`, no `allow-popups`, no `allow-forms` - matching the design in `ARCHITECTURE.md` section 5 precisely, not just trusting that what was typed into `index.html` survived the build copy unmodified.

**The "don't silently swap content mid-read" requirement needed a real state-tracking design, not just a comment.** `app.js` tracks two separate things: `viewingHash` (what's actually loaded in the iframe right now) and `lastKnownHeadVersion` (what the head was as of the last time the client synced with the server). A background refresh (SSE event or tab refocus) compares the freshly-fetched `headVersion` against `lastKnownHeadVersion`, not against `viewingHash` - conflating those two would have shown the "newer version available" banner every time a user deliberately clicked an older timeline entry to browse history, which is normal use, not a reason to nag them. Only an actual new head arriving triggers the banner; browsing past versions never does.

**Honest limit of what could be verified in this environment**: the full data flow (`GET /families` → `GET /families/:id` → `GET /content/:hash`) was verified end to end with real HTTP requests, and the HTML/CSS/JS were checked for structural correctness (balanced tags, valid JS syntax, the sandbox attribute landing correctly in the built output). The actual visual result of the redesign, and the client-side JS behavior that only runs in a real browser (the version-banner interaction, iframe loading, sidebar selection states), have not been seen or exercised by anyone, agent included - there is no browser-rendering or screenshot capability available here. This is flagged directly in the teaching document (`docs/understanding-docmanager-axi.html`) rather than left implicit, and the user needs to actually open `docmanager ui` and look before this can be called done, not just tested.

**Visual design decisions made, for whoever picks this up next**: a dark, fixed sidebar (independent of the light/dark theme toggle on the main content area) styled as a persistent "chrome," in the tradition of Linear/VSCode/Notion-style app shells, rather than a single flat theme throughout - this was a deliberate choice to read as a considered app rather than a generic themed page. A single muted indigo/violet accent (`#6d5ef0`) instead of a generic blue. Hand-written inline SVG icons (document, settings gear, folder, plus, warning) instead of an icon-font or icon-library dependency, consistent with the project's zero-framework, zero-extra-dependency stance for the UI. The version timeline was redesigned with a connecting rail and dot markers, deliberately visually closer to a git log graph than the original plain list.

## Confirmed findings from real user feedback on the reading pane (third review round)

The user actually opened the UI and found two real problems immediately - exactly the value of getting eyes on it rather than trusting "behavior-tested" as good enough:

**A genuine race condition, not a cosmetic bug.** `selectFamily()` and `refreshSelectedFamily()` both mutate `state.viewingHash`/`state.lastKnownHeadVersion`, but neither guarded against the other running concurrently. If a background refresh (SSE event or window focus) resolved while a `selectFamily()` call's own fetch was still in flight, the refresh compared the real fetched `headVersion` against `state.lastKnownHeadVersion`, which was still `null` at that point - `realHash !== null` is always true, so it read as "a new version arrived" when nothing had changed at all. This is exactly what the user saw: the "View latest" banner appearing immediately with no real new version behind it, and clicking it appearing to do nothing (it was clicking correctly and hiding the banner, but a second stale, already-in-flight refresh would land moments later and re-trigger it, and since the underlying content never actually changed, the iframe's `src` didn't visibly change either). Fixed with a `selectionToken` counter, bumped on every `selectFamily()` call; both `selectFamily()` and `refreshSelectedFamily()` check the token is still current before acting on their own resolved fetch, so a stale response can never overwrite state a newer selection has already superseded. The user's report also surfaced a real UX-clarity gap unrelated to the bug: "View latest" was read as something that should *create* a new version, when its only job is switching the reading pane to whatever the current head already is - versions are only ever created by an actual file edit on disk, never by a UI action. Worth remembering if this button's wording ever needs revisiting.

**The two-column layout (reading pane squeezed next to a 260px vertical timeline rail) was called out directly as too cramped**, contradicting the explicit goal ("read it the way you'd read it in your own browser tab, without compromising space"). Fixed with a real layout change, not a size tweak: the vertical timeline rail is gone, replaced with a horizontal scrollable strip of version chips sitting in a slim header above the reading pane, which now takes all remaining width and height edge-to-edge. An "Open in new tab" link was also added next to the title (`target="_blank"` to `/content/:hash`), giving a literal real-browser-tab escape hatch matching the user's own stated mental model, not just a bigger embedded pane.

**A real icon and spacing consistency audit, prompted by "sloppy and inconsistent" feedback that had no other specifics to go on.** Rather than guess blindly, the actual SVG icons across `index.html` and the dynamically-generated `DOC_ICON` in `app.js` were grepped and compared directly: sizes were inconsistently 13/14/15/16/20px and stroke-widths were inconsistently 1.2/1.3/1.4/1.6 across icons that should have read as one consistent icon set - one icon (the settings gear) even mixed two different stroke-widths within itself. Normalized to exactly two sizes used deliberately (16px/stroke-width 1.5 for every inline utility icon, larger sizes only for the brand mark and the empty-state illustration, both intentional exceptions) and a real spacing scale (`--space-1` through `--space-6`, replacing a scatter of close-but-not-quite-matching arbitrary rem values like 0.55rem vs 0.6rem vs 0.9rem) applied consistently throughout the stylesheet rather than left as a scatter of near-duplicate values.

**Honest limit, unchanged**: all of the above was verified through real HTTP requests (full family → content data chain), structural checks (balanced tags, valid CSS braces, valid JS), and direct inspection of the built output (the sandbox attribute, the normalized icon sizes). The actual visual result and the race-condition fix's real-browser timing behavior still have not been confirmed by anyone looking at a rendered page, including the agent - there is still no rendering or screenshot capability in this environment. This gap is real and stated directly to the user each time, not glossed over just because more rounds of fixes have happened.

## Two real daemon-lifecycle bugs found from the user's own "why am I seeing a reconnect banner" question

Not from planning - from the user asking a direct question about something they observed, which led to actually checking `ps aux` instead of guessing at a browser-side explanation.

**Orphaned daemons, caused by this session's own testing pattern but revealing a real product gap.** Across several responses, `rm -rf ~/.docmanager` was run to reset state between test rounds while a daemon from a previous "leave it running so the user can look" step was still alive. Deleting the directory removes the lock file a daemon is registered under, but the process itself keeps running - invisible to `ensureCoreRunning()`'s discovery, since that only ever looks at the lock file, never the process table directly. The next `core start` found no lock file and started a fresh daemon on a new port, leaving the old one as a live, leaked, silently-serving orphan. `ps aux` confirmed three separate `daemon.js` processes running simultaneously, started 7-9 minutes apart - not a hypothetical, an actual reproduced instance. This is not just a testing-habit problem: a real user deleting `~/.docmanager` manually, or a backup/restore, would orphan a running daemon exactly the same way. Fixed with a periodic self-check in `daemon.js` (every 15s): the daemon re-reads its own lock file and shuts itself down if it no longer identifies this process (missing, or a different pid) - verified directly, not assumed: started a daemon, deleted its lock file out from under it, and confirmed the process actually exited within the check interval and the lock file stayed absent afterward.

**`docmanager core stop` could hang forever with a browser tab open - found while cleaning up the orphans above.** `kill`ing the leaked daemons via `SIGTERM` left two of them stuck alive for well over the expected grace period. Root cause: the SIGTERM handler called `server.close(callback)` alone, which waits for every open connection to end on its own before firing its callback - an SSE stream is deliberately long-lived and never ends by itself, so with any browser tab connected, the callback (and the `process.exit()` inside it) would simply never run. Fixed by also calling `server.closeAllConnections()` (Node 18.2+, safe given `engines: node >=20`) alongside `server.close()`, forcing existing sockets shut immediately rather than waiting indefinitely. Verified directly: opened a real, held-open SSE connection via `curl -N`, then ran `docmanager core stop` and confirmed it completed in about 0.1 seconds instead of hanging, with the daemon process fully gone afterward.

## A third fix, same reconnect-banner thread: the dynamic port itself was the real root cause

Fixing the orphaned-daemon and hanging-stop bugs above did not actually make the reconnect banner go away, because those were contributing factors, not the root cause. The user asked directly: shouldn't docmanager always run on the same port, checking first whether one is already running before starting a new one? The singleton check already existed and already did that half - what was missing was port *stability*: the daemon bound to a randomly OS-assigned port on every fresh start (deliberately, to avoid colliding with unrelated local tools), which means every browser tab is only ever valid for one specific daemon instance and permanently breaks the moment that instance restarts on a different port, for any reason at all - a crash, a deliberate stop/start, anything.

Fixed by binding to a **fixed default port, `4389`**, continuing the sibling AXI tools' own established convention (lavish-axi: `4387`, reactive-axi: `4388`) rather than inventing a new pattern - only falling back to a random port if `4389` is genuinely occupied by something unrelated, overridable via `DOCMANAGER_PORT`. `lifecycle.js`'s existing "reuse last-known port on restart" logic now falls back to this fixed default instead of `0` (random) when there is no prior state, which also means it self-reinforces: once a daemon has ever bound `4389`, every future restart's "last known port" is `4389` too, so the whole system converges to always using it.

**Verified for real, not just reasoned about**: a completely fresh start bound `4389`; a simulated crash (`kill -9`) followed by a restart reused `4389` again; a normal stop-then-start also stayed on `4389`; and, the harder case, deliberately squatting a plain `http.createServer` on `4389` first and then starting docmanager confirmed the fallback still works correctly, landing on a random port without crashing or hanging. A full CLI regression pass confirmed nothing else broke from the change.

## A fourth fix, same reconnect-banner thread: idle-connection timeout and an over-eager banner

Fixing the port instability did not fully resolve it either - the user confirmed they were genuinely on `127.0.0.1:4389`, a fresh tab, and still saw the banner. This ruled out every hypothesis tested so far (stale tabs, orphaned daemons, the dynamic port). Two direct empirical checks against the *current, verified-healthy* daemon - a plain SSE connection held open briefly, and the same with a browser-realistic matching `Origin` header - both succeeded cleanly, ruling out an Origin-check false-positive too. What none of those checks exercised: real elapsed time. Both only held the connection open for a second or two; a real user leaving the tab open for minutes never got tested.

**The actual gap: an SSE connection can go completely idle indefinitely.** The server wrote one `:\n\n` comment when the stream opened and then nothing else unless an actual document change triggered a broadcast - meaning a connection with nothing to report could sit with zero bytes transferred for as long as the tab stayed open. This is a well-known class of problem for long-lived HTTP connections: browsers, OS network stacks, and local proxies can and do close a connection they perceive as dead from inactivity, even though nothing is actually wrong with either endpoint. Fixed with a periodic heartbeat (`:\n\n` every 20 seconds) in `handleEvents()`, verified directly, not assumed: held a real connection open for 25 seconds and confirmed via `od -c` that exactly the expected two comment writes arrived (the initial one plus one heartbeat tick at the ~20s mark).

**A second, compounding issue in the client, found from re-reading `EventSource`'s actual behavior rather than the server alone**: `onerror` fires on every connection drop, including the ordinary kind `EventSource` recovers from automatically moments later - the old code showed the banner on the very first error with no grace period, so even a connection that self-healed within a second would flash an alarming "lost connection" message. Fixed with a short grace timer (4 seconds): the banner only actually appears if the connection hasn't come back by the time the timer fires, and the timer is cancelled outright the moment `onopen` fires, so a routine reconnect is now invisible to the user rather than alarming.

**Honest note on this whole thread**: four different fixes came out of one user-reported symptom (orphaned daemons, a hanging stop, a dynamic port, and now SSE idle-timeout plus an over-eager banner), and each one was real and independently verified, but none of the first three were confirmed to be *the* cause until this one - the user's own report after each fix ("still seeing it") was what kept the investigation honest instead of declaring victory prematurely. Whether this specific combination is what the user was actually hitting still needs their confirmation - it cannot be verified from here, the same limitation as every visual/browser-only behavior in this project.

## The actual likely root cause of the whole reconnect-banner saga, found from a different, clearer bug report

The user reported two new, specific problems: the settings panel rendering underneath the document view instead of being properly separate, and the reading pane looking too short. Both traced to the exact same CSS bug reactive-axi's own project history documents hitting in its own chrome UI (`[hidden]` losing to a same-specificity class rule that also sets `display`) - a bug this session had direct, first-hand knowledge of before ever writing this stylesheet, and still shipped anyway. `.view { display: flex }` (governing the documents/settings top-level split) has equal CSS specificity to the browser's own `[hidden] { display: none }` default, and an author-stylesheet rule always wins over a user-agent rule at equal specificity - so `hidden` was being silently ignored on `#view-settings`, leaving both views rendered simultaneously, each getting roughly half the available height. That single collision explains both reported symptoms directly: the settings panel bleeding into view, and the reading pane only getting half its intended space.

**Checking for the same pattern elsewhere found three more instances of the identical bug**: `.detail`, `.version-banner`, and - the significant one - `.reconnect-banner` all independently set `display: flex` the same way. This means the reconnect banner most likely rendered unconditionally from every page load, regardless of actual connection health, this entire time. Every fix made in the two prior rounds chasing that banner (an orphaned-daemon self-check, a hanging `core stop`, a stable default port, an SSE heartbeat, a client-side reconnect grace period) was a real, independently-verified bug and worth having fixed on its own merits - but none of them could possibly have made the banner disappear, since its visibility was never actually gated by the `hidden` property working in the first place. Separately, `.version-banner` having the same bug more completely explains an even earlier symptom (the "View latest" banner appearing immediately on opening any document) than the race-condition fix from that round did - a CSS bug causing it on literally every document open is a better match for what was reported than an occasional timing race.

**Fixed once, globally, not four times individually**: a single `[hidden] { display: none !important; }` rule near the top of the stylesheet. `!important` in an author rule overrides any non-important declaration on the same property regardless of specificity, so this covers all four existing collisions unconditionally and makes any future element that is both `hidden` and has its own `display` declaration safe by construction, rather than relying on remembering to avoid the collision each time it's introduced.

**Also found and fixed in the same pass, real if minor**: a hardcoded color (`#100f13`) in the track-form textarea that bypassed the design-token system entirely (given a proper `--sidebar-input-bg` token instead), a missing `:hover` state on the track panel's summary (every other interactive sidebar element had one), and an unused `--radius-md` token that was defined but never referenced anywhere - removed rather than left as a loose end implying a design decision that was never actually made.

**Verified for real**: rebuilt `dist/ui` and confirmed the `[hidden]` rule and its `!important` are present in the actual served output, not just the source; a full CLI regression (`core start/stop`, `track`, `families`) confirmed nothing else broke. The visual result - whether the settings panel and reading pane now behave correctly, and whether the reconnect banner is now actually gone - still needs the user's own eyes, the same limitation as every prior round.

## Lifecycle completeness: idle timeout, an explicit stop path, and the Agent Skill

Three real questions from the user, none of them bug reports: was there an Agent Skill (there wasn't, a genuine gap against the `axi` skill's own guidance to ship both a session hook and a skill), did the background service ever stop on its own (no, and the reasoning for that decision, borrowed from lavish-axi/reactive-axi, doesn't actually transfer to docmanager's much shorter-lived interaction pattern), and did the lavish/reactive poll-based "tell the agent it stopped" model apply here (no, and the reason why is architectural: every `docmanager` CLI command is one-shot and exits completely, there is no long-lived agent-side process representing "someone is actively waiting" for the core to call back into, unlike `poll`, which genuinely is that process in the sibling tools).

**Idle timeout, confirmed by the user rather than decided alone**: asked directly whether to add an idle timeout, keep running forever with just a UI stop button, or both - the user chose both. `src/core/activity.js` (`markActivity()`/`idleMs()`) is updated on every incoming HTTP request and, critically, on every SSE heartbeat tick, so an open, connected UI tab counts as real activity even with zero new requests in between and never trips the timeout mid-use. `daemon.js` checks every 5 minutes (default) against a 4-hour default timeout, both overridable (`DOCMANAGER_IDLE_CHECK_INTERVAL_MS`, `DOCMANAGER_IDLE_TIMEOUT_MS`).

**A real test-design mistake, caught before it produced a false pass**: the first attempt to verify "an open connection prevents idle shutdown" used a 3-second idle timeout against the SSE heartbeat's hardcoded 20-second interval - the heartbeat could never fire in time to prove activity, so the daemon correctly (by the test's own broken math) shut down anyway, which read as a failure of the mechanism when it was actually a failure of the test's proportions. Made the heartbeat interval overridable too (`DOCMANAGER_SSE_HEARTBEAT_INTERVAL_MS`) and re-ran with a heartbeat genuinely shorter than the timeout (2s vs 6s, matching the real 20s-vs-4-hour production ratio) - confirmed correctly this time: the daemon survived twice the idle timeout duration with one held-open connection and no other requests.

**One canonical shutdown path, not four separate ones.** Before this round, the self-check and SIGTERM handler each independently called `server.closeAllConnections()`/`server.close()`. Adding two more triggers (the idle timeout, and a new UI-initiated stop) the same way would have meant four copies of the same shutdown logic to keep in sync. Introduced `src/core/shutdown.js` (`onShutdownRequested()`/`requestShutdown()`) as a single, idempotent, module-level convergence point - `daemon.js` registers exactly one listener that does the real work, and every trigger (SIGTERM, the self-check, the idle timeout, and the new `POST /core/stop` route) just calls `requestShutdown(reason)`.

**The UI's own stop action needed the response to genuinely outrace the shutdown**, not just be sent before it. The route handler schedules `requestShutdown()` via `setImmediate()` rather than calling it inline, so the JSON response has already been handed to the socket by the time the shutdown sequence starts - verified directly with a real `curl` request to `POST /core/stop`, confirming the `{"stopping":true}` response with a 200 status arrives before the process actually exits, not just assumed from the code's ordering.

**The Agent Skill**, `src/skill.js`/`scripts/build-skill.js`, mirrors the reactive-axi/lavish-axi pattern exactly: one function is the single source of truth, a `--check` mode catches a stale committed file, wired into both a dedicated `build:skill`/`build:skill:check` script and the main `build` script so publishing can never ship a stale skill silently. Command examples inside the skill use `npx -y --package=docmanager-axi docmanager <command>` rather than assuming a global install or a bin name matching the package name - deliberately unambiguous rather than relying on npx's implicit single-bin-fallback behavior, which was not verified precisely enough here to trust in a document real agents will actually follow. Verified: generation, `--check` passing when current, `--check` correctly failing after a hand-edit makes the committed file stale, and `npm pack --dry-run` confirming `skills/docmanager/SKILL.md` is genuinely included in what would actually publish.

**Also fixed while wiring the Agent Skill's guidance to match reality**: the README's own command reference table had gone stale since the batch/folder-tracking feature shipped - still showed `docmanager track <path> [--as <path>] [--relink]`, no mention of multiple paths or folders. A README documenting a real, published-facing tool drifting from what the CLI actually does is exactly the kind of thing worth catching proactively, not just when someone notices.

## Settings page: clipping bug and wasted space, both from the same review, one CSS bug and one real layout decision

**A second real instance of "overflow-y:auto is inert without a height constraint," a different variant of the earlier `[hidden]` cascade bug, same underlying category of mistake.** `.panel` was styled `height: fit-content; overflow-y: auto;` - but `fit-content` means the element grows to whatever its content needs rather than being bounded, so its own `overflow-y: auto` never actually had anything to trigger on. The growing content (three `.info-block` sections, including the new danger-zone) eventually exceeded the viewport, and `.content`'s `overflow: hidden` further up the ancestor chain silently clipped whatever didn't fit - the "Stop docmanager" button, being the last element, was the first thing cut off. Fixed by moving the scroll responsibility to the actual container that's height-constrained (`.settings-layout`, `flex: 1; min-height: 0; overflow-y: auto`) rather than an inert property on an unconstrained child.

**The wasted-space complaint led to an actual layout redesign, not a width tweak.** Rather than just widening one card, split settings into two panels side by side: a focused, fixed-width primary column (`.settings-primary`, 400px - the actual form plus the stop-service action, both real user decisions that benefit from a narrower, more scannable width) and a flexible reference column (`.settings-reference`, `flex: 1` - the explanatory content about remote URL formats and what a snapshot contains, which benefits from the extra width for readability and the existing two-column included/excluded grid). This solves both complaints from one structural change: no more empty right-hand space, and less total vertical height per column, directly reducing how likely any future growth is to hit the clipping ceiling again. A responsive breakpoint (900px) stacks the two panels vertically on narrow viewports.

**A real mistake caught during the edit, not after**: while restructuring the HTML, the `hidden` attribute was accidentally dropped from `#view-settings` itself, which would have made the settings view visible by default on page load - caught by grep-checking for all four `hidden` occurrences in the file before rebuilding, not discovered visually (still no rendering capability here).

**A related, smaller inconsistency fixed in the same pass**: the reference panel's first `.info-block` now has no preceding sibling within its own panel, so its separator border/margin would read as an orphaned line with nothing above it to separate from. Fixed with `.panel > .info-block:first-child { border-top: none; ... }`.

## A real, reproduced port-race bug, found while testing the settings fix, unrelated to it

While rebuilding and testing the settings-layout fix, a `core stop` immediately followed by `core start` landed on a random port instead of the fixed `4389` - a real, observed failure, not a hypothetical. Root cause: right after a daemon stops, the OS can briefly still report the just-vacated port as in use (a TIME_WAIT-style condition) before a new bind is allowed to succeed - `daemon.js`'s port-selection previously gave up and fell back to random on the very first `EADDRINUSE`, with no tolerance for this transient window. This directly undermines the entire point of the fixed-port fix from an earlier round: a stop-then-immediately-start sequence (a completely ordinary real workflow: click stop, then run a command) could silently regress back to an unpredictable port.

Fixed with a bounded retry: up to 5 attempts, 200ms apart, on the preferred port before falling back to random - absorbs the transient release window without changing behavior for a port that's genuinely, permanently held by something unrelated. **Verified with three separate, deliberately isolated real scenarios**, not assumed from the code: (1) a real squatting server that releases port 4389 after 700ms, confirmed docmanager retries through the window and lands correctly on 4389, not a random port; (2) a real squatting server that holds the port indefinitely, confirmed docmanager exhausts its retries (about 1 second, matching 5x200ms) and correctly falls back to random rather than hanging; (3) a full regression of the self-check and `/core/stop` mechanisms confirming neither regressed from the `start()` function rewrite. The first attempt at test (2) produced a confusing, seemingly-contradictory result from stale background processes left over from earlier test rounds polluting the same port and process list - resolved by doing a full, deliberate process cleanup and re-isolating each scenario, rather than trusting an ambiguous result.

**Not yet exercised: an actual browser session.** `docmanager ui` itself (the `open()` call that launches a real, visible browser window) was deliberately never run during this testing pass - popping a real browser window on the user's screen as a side effect of automated verification isn't something to do without it being asked for. The HTTP layer underneath it is thoroughly verified above; the actual rendered page, click interactions, and focus-triggered refetch behavior are not. Worth a real manual check before considering the UI truly done, not just "the API it calls is correct."

## Thirteenth round: the duplicate-suggestion heuristic, `docmanager doctor`, and a real class of bug the test suite immediately paid for itself on

Continuing the saved production-readiness/feature plan, the user asked to proceed to item 2: the two things already committed to v1's own original scope but never built. The user's framing this round was explicit and worth taking literally - "ensure all gaps are covered... no loose ends or bugs" - so this round leaned harder on manual adversarial testing (deliberately planting corruption) than a normal feature round would, and it paid off immediately.

**The duplicate-suggestion heuristic** (`src/core/suggest.js`) compares every pair of currently-tracked families on two independent, cheap signals: a normalized title match (each document's own `<title>`, falling back to its first `<h1>`, with common suffixes like "final"/"draft"/"copy"/"v2" stripped via a bounded-iteration regex before comparing - bounded to avoid stripping a legitimately short, all-suffix-looking real title down to nothing) and a structural fingerprint (a sha256 hash of the tag sequence alone, via `parse5` - the same HTML parser `html-normalize.js` already uses - deliberately ignoring text/attributes, so two documents built from the same template share this exactly even with completely different content). Either signal alone triggers a suggestion. Wired into `GET /families`'s response as `suggestedLinks`, surfaced in `docmanager families`/`status` as `possibleDuplicates` with an explicit "never auto-linked" help line, and given a light-touch UI treatment (a small badge on affected sidebar items, title-tooltip only, no new "link" action added to the UI - `link` stays CLI-only, matching existing scope). Verified directly with real fixtures: a title-only match (deliberately given different tag structure so the test isolates the signal), a structural-only match (deliberately given different, unrelated titles), and a genuinely unrelated pair producing zero suggestions.

**`docmanager doctor`** (`src/core/doctor.js`, `GET /doctor`) checks git availability, store/git validity, family-record JSON integrity, content-blob referential integrity (every version's content blob actually exists on disk, not just the head version's), a full index rebuild, and local-state mapping consistency. Deliberately split into two tiers, not left as one undifferentiated "repair everything" action: **auto-repaired** (rebuilding the SQLite index - already explicitly derived/disposable data per this project's own architecture, and a mapping whose family has *genuinely and verifiably* ceased to exist, i.e. `getFamily()` returns `null`, not merely throws) vs. **report-only, never touched** (a family record that fails to parse, a version whose content blob is missing) - these could represent real, unrecoverable document data, so deciding what to do about them is the user's call, the same approval-gating principle this project already applies to the reset/uninstall command and autonomous `git` installation. `checkGit()` deliberately calls `spawnSync` directly rather than reusing `git.js`'s `assertGitAvailable()`, specifically so a diagnostic tool always reflects present-moment reality rather than a cached assumption from earlier in the process's life - this also conveniently sidesteps `git.js`'s own process-lifetime caching gotcha (see `git.test.js`'s comment) without any special test isolation needed.

**A real, previously-hidden production bug found by doctor's own repair pass, not hunted for deliberately**: while manually verifying doctor against a deliberately corrupted family JSON file, `docmanager doctor` itself crashed - and so, it turned out, did `docmanager families`/`status`. Root cause, found in three different places by tracing the actual stack: `store.js`'s `getFamily()` throws on invalid JSON with no try/catch of its own (by design - it's a low-level read), but **nothing calling it in a loop over every family guarded against that** - `index.js`'s `rebuildIndex()`, the brand-new `suggest.js`'s `analyzeFamily()`, and `reconcile.js`'s per-mapping loop all called it unguarded. A single corrupt family file was silently capable of taking down the entire index rebuild (and by extension `docmanager families`/`status` the next time either needed rebuilding), not just reporting a problem with itself. This is exactly the kind of cascading-failure bug the plan's own stated rationale for building a test suite first was worried about, and it was caught by the same discipline that motivated it - real adversarial testing, not just reading the code. Fixed identically in all three places: wrap the per-family `getFamily()` call in its own try/catch and skip that one family, never letting one bad record take down every other healthy one. `reconcile.js` additionally gained a real, distinct `corrupt` status (previously would have thrown; a related previously-silent `orphaned-mapping` status also got surfaced in the CLI's `families`/`status` output for the first time, since leaving either one silent while fixing the crash would have traded a crash for quiet data-hiding).

**A second, more subtle bug caught in the same manual pass, this time in doctor's own new code**: `checkLocalState()`'s orphan-cleanup filter also called `getFamily()` unguarded, so a local-state mapping pointing at a *corrupt* (not missing) family crashed doctor too. Fixing this needed a real design decision, not just a try/catch: a mapping to a family that's **corrupt but still present** must NOT be treated the same as a mapping to a family that's **genuinely gone** (`getFamily()` returning `null`) - auto-deleting the mapping in the corrupt case would compound potential data loss (the underlying family record might still be recoverable, e.g. from the store's own git history), whereas deleting a mapping to something that's actually gone is safe by construction. `familyIsGenuinelyMissing()` distinguishes the two explicitly (`try { return getFamily(id) === null } catch { return false }`), verified directly: a mapping to a corrupt family survives doctor untouched and is reported as "valid" by `localState` (since the mapping itself isn't the problem - `familyIntegrity` is what reports the real issue), while a mapping to a truly nonexistent family gets cleaned up automatically.

**Verified for real, end to end, both automated and manual**: 15 new tests (`suggest.test.js`, `doctor.test.js`, two additions to `cli.test.js`) plus the three defensive fixes above, all planting real corrupted fixtures (invalid JSON, a deleted content blob, orphaned and corrupt-pointing local-state mappings) rather than only asserting the happy path - full suite now 46/46. Also manually verified against the real, live `~/.docmanager` store (not just isolated test fixtures): the dev daemon had to be restarted to pick up the new `/doctor` route (daemons don't hot-reload source changes, expected, not a bug), after which `doctor` reported all 6 checks `ok` against the real store, and `families` correctly showed no false-positive `possibleDuplicates` between the two real, unrelated tracked documents.

## Fourteenth round: diff between versions and revert to an older version - a real design correction worked out before writing code, not after

Continuing the plan's own sequencing to item 3. Before implementation, the user asked a genuinely clarifying question: does revert touch the real file on disk? The first-pass answer given ("no, recorded as a new version") turned out to be half-wrong once the content-addressed model was worked through precisely, and this got corrected in the plan itself before any code was written, not silently changed after the fact. Versions are keyed by content hash, and hash is deterministic - reverting to old content can never produce a genuinely new, distinct hash, only collide with the hash that content already has. Naively reusing `recordVersionIfChanged` for revert would have silently overwritten that existing entry's own `createdAt`/`supersedes` fields, actively corrupting lineage the same way the phase-5 reconciliation bug once did for real. The corrected, much simpler mechanics: **`revertToVersion()` (`src/core/store.js`) just moves `family.headVersion` back to an already-known hash** - no version added, none removed, full history stays fully visible (the UI's timeline already renders chronologically regardless of the supersedes chain, so this needed zero UI redesign). This is the direct equivalent of moving a git branch pointer to an earlier commit without deleting anything newer.

**This design composes with existing machinery with genuinely zero special-casing**, confirmed directly rather than assumed: `reconcile.js`'s `behind-head` status (built in phase 5 for the cross-machine-pull case - a live file whose content matches a known-but-not-current version) already handles a live file that's "ahead" of a freshly-reverted head, with no new code needed at all. Verified with an integration test spanning `revertToVersion`/`trackPath`/`reconcile` together, and with a real manual test: revert, then check the real file's sha256 checksum before and after - bit-for-bit identical, cryptographic proof rather than a visual check that the real file is genuinely untouched.

**Diff** (`src/core/diff.js`'s `diffVersions()`) settles its one real open design question by simply reading `ARCHITECTURE.md` section 3.4, written before diff ever existed: *"The diff shown to the user is computed on the normalized form, not the raw bytes."* Reuses `html-normalize.js`'s `normalizeHtml()` exactly as-is - zero risk to the equality-comparison logic it's used for elsewhere - plus one new, deliberately separate, display-only function, `prettyForDiff()`, which inserts a newline before every tag so the normalized output (which drops whitespace-only text nodes entirely, correct for equality checks but unreadable as a line diff) becomes line-shaped enough to diff meaningfully.

**A real, deliberate new dependency: `diff` (jsdiff)**, not a default reflex. A hand-rolled line-diff algorithm (Myers/LCS) has genuine, easy-to-get-wrong edge cases, and getting it wrong produces a directly user-visible wrong answer - this project already added `parse5` and `better-sqlite3` specifically when correctness mattered more than staying dependency-free, and the same reasoning applies here. Confirmed the package's real ESM export shape directly (`import { diffLines } from "diff"`) before writing code against it, rather than assuming from memory. The API returns the structured diff parts (`{ value, added, removed }`) rather than pre-formatted text, so the CLI's plain-text unified-style render and the UI's colored render both come from one shared computation - this project already deleted a duplicated derivation once, on principle, and this avoids creating a new one.

**Verified end to end**: 12 new tests (`revert.test.js`, `diff.test.js`, two CLI smoke additions) plus a precise test directly proving `ARCHITECTURE.md` section 3.4's claim - two distinct stored versions whose raw bytes differ (so they're legitimately separate entries) but whose normalized form is identical diff as having zero real changes - full suite now 58/58. Manually verified via `curl` against the exact `GET /families/:id/diff` shape the UI's new compare panel consumes, confirming the response matches what `app.js` actually reads field-for-field (the same "test the real API shape the client depends on" discipline used throughout this project). The UI additions (a "Revert to this version" button, a collapsed "Compare versions" `<details>` panel reusing the track-panel's existing disclosure pattern, colored diff output) were verified structurally (present in the built `dist/ui` output, syntax-checked) but not in an actual browser session - same standing limitation as every UI round in this project's history.

## Fifteenth round: basic keyword search (SQLite FTS5), a real refactor to avoid duplicating title-extraction, and a text-extraction bug caught by actually reading the output

Item 4 of the plan: cheap, non-semantic full-text search - explicitly not RAG (still correctly deferred), just answering "where's the document about X" from words that are actually in it. First verified the load-bearing assumption directly rather than assuming: does this project's real `better-sqlite3` build actually have FTS5 compiled in? A throwaway `CREATE VIRTUAL TABLE ... USING fts5` against an in-memory DB confirmed yes, before any further design happened.

**A real, deliberate refactor before writing new code**: `suggest.js` already had its own private `findFirstText`/`extractTitle` for the duplicate-suggestion heuristic. Search needed the exact same "what does this document call itself" signal. Rather than write a second copy (exactly the class of duplicated derivation this project has explicitly avoided before, once by deleting one on principle), moved `extractTitle` into `html-normalize.js` as a shared, exported function and updated `suggest.js` to import it - one implementation, two callers. Added a new sibling function, `extractPlainText()`, for the genuinely new need: the document's visible text stripped of markup, for indexing search's `body` column.

**A real bug caught by reading the actual snippet output, not by trusting the code**: the first version of `extractPlainText()` only excluded `<script>`/`<style>` from text collection, so a document's own `<title>` (physically a text node inside `<head>`) got folded into the "body" text meant to represent visible page content. A manual smoke test's search result snippet showed the title text bleeding into what should have been pure body content ("Q3 Financial Report Revenue grew significantly this **quarter**..."), immediately visible as wrong once actually looked at rather than assumed correct because the code "looked right." Root cause: nothing under `<head>` is ever rendered as visible content, and the function's own docstring already claimed "the document's visible text" - the implementation just didn't match that claim yet. Fixed by excluding the entire `<head>` subtree (not just `<script>`/`<style>` individually) from body-text collection, keeping `doc_title` as FTS's own separate, deliberate signal rather than redundantly duplicated inside `body` too. Re-verified: the same search now returns a clean, body-only snippet.

**Schema and query design**, `src/core/index.js`: a new `search` FTS5 virtual table (`family_id UNINDEXED, synthetic_path, doc_title, body`, `tokenize = 'porter unicode61'`) populated inside the same `rebuildIndex()` transaction every other change already triggers - no separate index-maintenance path to keep in sync. Indexes HEAD version content only (a stale historical draft surfacing in "current state" search would be confusing, not helpful). Reused the exact same corrupt-family defensive pattern fixed in the thirteenth round (`try { getFamily(id) } catch { continue }`) and additionally handles a missing content blob gracefully (insert a row with just the synthetic path, still findable by path even with no indexed body/title) - both verified with real planted-corruption tests, not just the happy path.

**Query safety, not just correctness**: raw user input can't be handed to FTS5's MATCH operand directly - quotes, hyphens (NOT), and colons (column filters) are all syntactically meaningful to FTS5's own mini query language, and unsanitized input could throw a syntax error or silently mean something the user never intended. Every whitespace-split term gets individually double-quoted and prefix-matched (`"term"*`, internal quotes escaped), joined by FTS5's default implicit AND - safe against injection by construction, and a forgiving prefix match besides. Verified directly with a `bm25(search, ...)`/`snippet(search, N, ...)` compatibility check first (confirming the alias-vs-bare-table-name question empirically rather than guessing - SQLite resolves an FTS5 function's table-name argument correctly even when the table is aliased in the surrounding query) before writing the real query.

**One shared computation, two renderers, again**: the server marks matched snippet terms with a plain `**term**` convention (not HTML) - the CLI shows it as-is (a reasonable plain-text emphasis convention for a terminal), and the UI's new `highlightSnippet()` escapes the real document text first, then turns `**...**` into `<mark>` tags on the already-escaped string - safe by construction, one shared computation, matching the same pattern already used for diff's structured parts.

**Verified end to end**: 10 new tests (`search.test.js`, two CLI smoke additions) covering matches on body/title/path, multi-word implicit-AND, genuinely-no-match and empty-query cases, missing-content-blob resilience, and corrupt-family resilience - full suite now 68/68. Manually verified against the real, live `~/.docmanager` store: `docmanager search doctor`/`docmanager search axi` both returned the real teaching document with a genuinely relevant, correctly-highlighted snippet pulled from its actual current content.

## Sixteenth round: deleting a single version, requested directly by the user ahead of the plan's own next item

The user asked for the ability to permanently discard one version shown in the UI (a delete/cross icon next to a version chip), specifically because "the user doesn't want to track previous versions" anymore after moving on. Explicitly out of the plan's own sequence - implemented immediately, ahead of the fresh-machine git-auth work, since the user asked for it directly.

**This is a meaningfully more consequential operation than revert, and needed real design work before any code**, not just a thinner variant of the existing revert/untrack pair. Three real questions had to be answered up front:

1. **What happens to the supersedes chain when a MIDDLE version is deleted?** A dangling pointer (a version whose `supersedes` references a hash that no longer exists) would corrupt the very lineage this project has fought hard to protect twice already (see the phase-5 reconciliation bug and the revert-semantics correction from the fourteenth round). The correct behavior, chosen deliberately: whoever superseded the deleted version gets re-linked to the deleted version's own parent - the exact equivalent of `git rebase --onto`/dropping a commit from history. Deleting a root version makes its child the new root (`supersedes: null`); deleting a head version moves `headVersion` back to that version's own parent (identical mechanics to an implicit revert, combined with actually discarding the record).
2. **What happens to the content blob?** Left untouched, following the exact precedent `deleteFamily()` already set in an earlier round: content is hash-addressed and possibly shared across multiple versions or even multiple families, so deleting the blob here isn't safe in general. `deleteVersion()` only ever removes the metadata record.
3. **What about a family's ONLY remaining version?** Refused outright with a new `CANNOT_DELETE_LAST_VERSION` error pointing at `untrack` - deleting the last version would leave a family with zero versions, breaking a fundamental invariant every family has held since it was first created. "Get rid of the whole document" already has a real, correct action; this isn't it.

**Implementation** (`src/core/store.js`'s `deleteVersion(familyId, hash)`, inside the same `serialize()` write queue every other mutation uses): re-links every entry whose `supersedes` matches the deleted hash to the deleted entry's own parent (a loop over all entries, not just an assumed single child - defensive against a theoretical non-linear graph even though this codebase's real history is always linear in practice), moves `headVersion` if the deleted version was current, refuses on the last-version case before touching anything. Wired through the identical stack every other mutation uses: a new `DELETE /families/:id/versions/:hash` route (the first real use of the DELETE HTTP method in this codebase - proper REST semantics for "remove a resource" rather than overloading POST again), `coreClient.deleteVersion()`, a new `docmanager families delete-version <id> <hash>` CLI subcommand, and a small delete icon on each UI version chip (hidden entirely when a family has only one version left, so the UI never even offers an action the store would refuse) with `event.stopPropagation()` so it doesn't also trigger the chip's own "view this version" click, and a confirm dialog whose wording differs depending on whether the target is the current head or a past version.

**Verified for real, both isolated and manually**: a three-version chain (`v1→v2→v3`) used to test all three chain-healing scenarios precisely - deleting the middle (`v2`) correctly re-points `v3.supersedes` to `v1`; deleting the root (`v1`) correctly makes `v2` the new root; deleting the head (`v3`) correctly moves `headVersion` back to `v2`. A dedicated integration test confirmed the exact interaction predicted during design: after deleting a head version, if the live tracked file on disk still holds that exact deleted content, the next `reconcile()` correctly re-captures it as a genuinely new version (a fresh entry at that same hash, since the old entry is gone) rather than silently losing it - `new-version-captured`, not a crash or silent no-op, confirmed empirically rather than just reasoned about. **A real bug, found immediately by the user actually using the delete button in the UI, not by anything in this test suite**: `family.versions.slice is not a function`. ## Seventeenth round: fresh-machine git auth - an HTTPS access token and a read-only SSH diagnostic

Item 4a of the plan, continued after the ad-hoc delete-version detour. Two genuinely different remote styles need two different answers, and the design (worked out in the plan itself before this round started) drew a hard line the implementation had to respect exactly: the HTTPS-token half is a plain settings feature: the SSH half must never let docmanager or an agent generate or modify anything in `~/.ssh` autonomously - the same class of action as installing `git`, which already requires the user's explicit, in-the-moment approval every time.

**Redaction lives at the API boundary, not the storage layer.** `settings.js` gained a new `snapshotRemoteToken` field, stored and returned plainly - `snapshot.js` needs the real value to actually authenticate, so hiding it inside `settings.js` itself would have broken that. Instead, `server.js`'s `GET`/`PUT /settings` routes both pass the result through a new `redactSettings()` helper that strips the raw token and replaces it with a `snapshotRemoteTokenSet` boolean before it ever leaves the process. A dedicated regression test hits the raw HTTP routes directly (not just CLI-rendered text, matching the discipline the `family.versions` shape bug just established) and asserts the literal string of the configured token never appears anywhere in either response body.

**The token is injected ephemerally, never persisted anywhere but `settings.json`.** `snapshot.js`'s `authArgs(url)` returns `["-c", "http.extraheader=AUTHORIZATION: basic <base64>"]` only when the configured remote is genuinely HTTPS (`isHttpsRemote()`) and a token is actually set - empty for an SSH remote or a local bare-repo path, silently and correctly a no-op rather than an error. Prepended as a global option immediately before the git subcommand on exactly the three network-touching calls (`clone`, `fetch`, `push`) - never on the purely local `remote add`/`set-url` calls, which don't need it and shouldn't carry it. Verified as a pure function directly (empty-token, non-HTTPS, and real-HTTPS-with-token cases, decoding the base64 back to confirm the exact `x-access-token:<token>` format), and verified end to end that a configured token never breaks the existing real local-bare-repo push/pull tests - `authArgs()` correctly no-ops for a non-HTTPS remote, so nothing about phase 5's original two-machine test needed to change.

**SSH auth failures get a real, actionable structured error instead of git's raw stderr.** `snapshot.js`'s `translateNetworkError()` inspects the caught error's message for git's own real, well-known failure wording (`permission denied (publickey)`, `host key verification failed`) on the `clone`/`fetch`/`push` calls specifically, and raises a distinct `SSH_AUTH_FAILED` pointing at `docmanager setup ssh` instead of falling through to the generic `PUSH_REJECTED`/raw-error path.

**`src/core/ssh-check.js` is deliberately, entirely read-only - this was the actual hard part of the round, not the token half.** It finds existing SSH public keys and reports them, extracts the host from an SSH-style remote URL, and tests real connectivity via `ssh -T git@<host> -o BatchMode=yes` - but never writes to `~/.ssh` and never calls `ssh-keygen`. A real, non-obvious gotcha handled correctly: GitHub (and most modern git hosts) intentionally deny shell access even on a **fully successful** SSH auth, replying over stderr with "successfully authenticated" and exiting non-zero regardless - so success has to be read from the message text, never the exit code. `classifyConnectionOutput()` is exported specifically so this exact classification logic could be unit-tested with real, canned GitHub wording rather than depending on live network access in the automated suite (the actual `ssh -T` network call itself is intentionally NOT part of the automated tests - too environment-dependent, matching this project's own established caution about flaky external dependencies - but it WAS run for real, manually, against this session's actual GitHub account and real SSH key, and correctly reported success). When no key exists at all, the CLI/UI output explicitly tells the agent that generating one is the user's call, never docmanager's - encoded as a new hard rule in `AGENTS.md` right next to the existing git-install rule, not left as an unwritten expectation.

**Verified for real, end to end**: `docmanager setup ssh` run manually against three real scenarios - no remote configured, an HTTPS remote (correctly reports the check doesn't apply), and the real dev machine's own actual SSH-style snapshot remote (`git@github.com:...`), which correctly found the real `~/.ssh/id_rsa.pub` key and reported a genuine successful connection to `github.com` - a live, unmocked, real-world pass, not a simulated one. `docmanager settings set --snapshot-remote-token`/`settings get` manually verified for the full lifecycle: set alongside the remote, update the token alone without disturbing the remote, and clear it - `snapshotRemoteTokenSet` transitioning correctly at every step, raw value never appearing in any output. 19 new tests (`settings.test.js`, `ssh-check.test.js`, `snapshot-auth.test.js`, two `cli.test.js` additions), full suite now 97/97.

## Eighteenth round: rendered, side-by-side diff highlighting - reading a change, not auditing its markup

The user asked for a genuinely different way to view a diff: the existing source-line diff was "okay" but not what a reader wants - they wanted both versions opened as actual rendered pages, side by side, with the changed parts highlighted red/green directly on the rendered document. A real, substantial addition, not a restyling of the existing diff output.

**The real design decision was granularity, and it was made deliberately in favor of safety over precision.** A word-level approach (diff the visible text, splice `<ins>`/`<del>` markers back into arbitrary text runs) is what a "proper" visual diff tool would do, but it risks producing broken or mismatched markup whenever a diffed span crosses an element boundary - a real, known failure class for exactly this kind of tool. The chosen design instead operates at the **block level**: `diff.js`'s `renderHighlightedContent()` identifies "leaf content blocks" (`<p>`, `<li>`, headings, table cells, blockquotes... - a block tag that doesn't itself contain another block tag, falling back to `<body>`'s direct element children for a document built from nothing but `<div>`s), diffs the ORDERED SEQUENCE of block contents with `diffArrays()` (the same `diff` package, its sequence-diff mode rather than line mode), and only ever adds a `data-diff="removed"`/`"added"` attribute to a block that's already exclusive to one side - never splits, moves, or reconstructs markup. This is safe by construction: since every marked node already existed in the tree, there's no way to produce invalid HTML, at the honest cost of coarser highlighting (a paragraph with one changed word highlights as a whole paragraph, not word-by-word). Verified empirically before writing the route: `parse5.serialize()` given a single element node returns its INNER content (not a self-wrapping outer tag) and mutating a node's `.attrs` array before re-serializing the whole document correctly reflects the change - both load-bearing assumptions checked directly rather than assumed.

**Served as raw HTML at a new route, `GET /content/:hash/diff-against/:otherHash?mode=removed|added`**, the same pattern as the existing `/content/:hash` route (raw bytes, not JSON, kept outside the JSON `ROUTES` table, its own `handleContentDiff()`). The highlighting has to live *inside* the served document itself, not be applied by the parent page - the UI's two comparison panes are sandboxed iframes (`allow-scripts`, no `allow-same-origin`), so the parent page genuinely cannot reach into either one to style it, by design (the same security property the reading pane already relies on). `mode` is purely a labeling choice for which color applies to that hash's own exclusive blocks; the underlying block-matching logic is identical either direction, so the route calls the same function symmetrically for both the "from" and "to" panels.

**The UI's Compare panel gained a Text/Rendered toggle**, not a replacement - the existing source-line diff stays available (still the right tool for precision or scripting), and "Rendered" swaps the `<pre>` output for two side-by-side sandboxed iframes pointing at the new diff-against URLs. One real CSS bug caught and fixed before it shipped: `.reading-frame`'s own base rule sets `flex:1`, which carries an *implicit* `flex-basis:0%` - in a flex-column parent, that would have silently overridden an explicit `height:420px` on the comparison iframes and collapsed them to near-zero height. Fixed by setting `flex:none` explicitly in the overriding rule so `height` actually governs sizing in this context - caught by reasoning through the flex box model before it ever rendered wrong, not after.

**Two real test-writing mistakes caught on the first run, both in the tests, not the product** - a healthy, now-familiar pattern in this project: the injected `<style>` block's own CSS selector text (`[data-diff="removed"]{...}`) legitimately contains the substring `data-diff` regardless of whether anything was actually marked, so a bare `doesNotMatch(html, /data-diff/)` assertion always failed even when nothing was wrong, and a bare occurrence-count regex over-counted by exactly one (the CSS selector itself) every time. Fixed by asserting on the HTML *attribute* form specifically (` data-diff="removed"`, space-prefixed, distinct from the CSS's bracket-prefixed form) rather than the bare substring - both failures traced by hand to the actual cause before "fixing" anything, confirming the underlying feature was correct the whole time.

**Verified end to end**: 10 new tests (`render-diff.test.js`, one `cli.test.js` HTTP-level addition covering the real route with valid/invalid hash/mode combinations and a genuine 404), full suite now 104/104. Manually verified against the real, live teaching document's actual multi-round edit history (not just synthetic fixtures) - both directions of a real diff-against call against real content returned exactly 5 matching highlighted blocks each, a sane, symmetric, real-world result.

## Nineteenth round: the rendered diff needed real UX work, not just the underlying mechanism - a dedicated modal and synced scrolling

The user actually used the rendered diff from the eighteenth round and reported it back accurately: it opened crammed into the same scrolling view as the timeline and reading pane, cluttered rather than clean, and the two panes had to be scrolled independently by hand. Both are real, valid UX gaps in what shipped, not new feature requests - the underlying highlighting mechanism from the previous round was correct and stayed untouched; only how it's presented needed rework.

**A dedicated full-screen modal replaces the inline `<details>` panel entirely, for both Text and Rendered modes** - not just Rendered, since having two different interaction patterns for what's conceptually one feature (an inline disclosure for one mode, a modal for the other) would have been its own inconsistency. The trigger is now a plain button ("Compare versions", styled like the existing "Open in new tab" affordance) sitting between the timeline and the reading pane, replacing the old always-visible `<details>` element entirely - a much smaller footprint in the normal reading view, opening the full comparison experience only when actually wanted. The modal (`#compare-modal`, a `.modal-overlay`/`.modal-dialog` pair - the first modal UI this project has built, a real, reusable pattern now available for anything else that needs one) covers most of the viewport (`min(1200px, 100%)` × `min(820px, 100%)`), closes on the × button, clicking the backdrop, or Escape, and `selectFamily()` defensively closes it whenever the user picks a different document so a stale comparison can never linger referencing the wrong family. Closing also resets both iframes to `about:blank`, stopping their content (and the scroll-sync script within it, see below) from continuing to run invisibly in the background.

**True synchronized scrolling required `postMessage`, not direct DOM access - a real technical constraint from the same sandbox model, not an implementation shortcut.** The two comparison panes are `sandbox="allow-scripts"` iframes without `allow-same-origin` (deliberately, per section 5 - the isolation between a tracked document and docmanager's own data is the whole point), which means the parent page has no way to read or set either iframe's `scrollY` directly - that's the browser's same-origin policy doing exactly what the sandbox was chosen for. `postMessage` is the one channel that still crosses that boundary by design. The fix: `diff.js`'s `renderHighlightedContent()` now injects a small script (`SCROLL_SYNC_SCRIPT`, alongside the existing highlighting `<style>`, via a generalized `injectIntoHead()` replacing the old `injectStyle()`) into each served comparison document - it reports its own scroll position as a **ratio** (not a pixel offset, since the two versions are almost never the same length) via `postMessage` on every scroll event, and applies an incoming ratio the same way. The parent page (`app.js`) just relays: on receiving a ratio from one iframe, it posts the same ratio to the *other* one, identifying the sender via `event.source` (a valid, comparable window reference even across an opaque sandbox origin - confirmed this actually works as expected, not assumed) rather than trusting anything else about the message. A `syncing` boolean guards the receiving side against re-triggering its own outbound message when the programmatic `scrollTo()` call fires a native `scroll` event - without it, the two panes would ping-pong into each other indefinitely.

**A new test locks in the script's presence** (`render-diff.test.js`) - checking for `<script>`, `postMessage`, and the `docmanager-diff-scroll` message-type string in the served output, since this is now a real, load-bearing part of the feature that a future refactor could silently drop without any other test noticing (nothing else exercises actual scroll behavior, since there's still no browser-rendering capability in this environment). Verified for real: the built output was manually inspected and confirmed the injected script is syntactically well-formed alongside the existing highlighting styles; full suite (105/105) confirms nothing about the underlying block-matching logic changed.

**Still honestly unverified, same standing gap as every UI round**: the actual modal layout, the close interactions (Escape/backdrop/×), and the synced-scroll *feel* in a real browser have not been seen by anyone, agent included - there is no rendering capability in this environment. The user needs to open `docmanager ui` and try it themselves before this round is genuinely done, the same as every prior UI change in this project's history.

**A same-round follow-up, from the user actually trying it in a real browser**: two real, concrete complaints - the synced scroll was jittery, and the modal read as small on their actual screen. Both fixed without touching the underlying block-highlighting logic at all.

*Scroll jitter, root-caused rather than patched blindly*: the original `SCROLL_SYNC_SCRIPT` posted a message on every raw `scroll` event with no throttling - a fast trackpad/wheel gesture fires far more of those than the message-passing round trip (iframe → parent → other iframe, each hop an async postMessage) could keep up with, so the follower pane visibly lagged and caught up rather than moving in lockstep. Fixed by throttling outgoing reports to once per `requestAnimationFrame` tick via a `reportScheduled` flag. A second, subtler bug in the original guard: `syncing` released on `requestAnimationFrame`, but the native `scroll` event a programmatic `scrollTo()` produces fires asynchronously with no guaranteed ordering against rAF - it could slip through the guard before actually firing, letting a stale correction bounce back to the original sender and visibly stutter. Fixed by releasing `syncing` on a 120ms `setTimeout` instead, which reliably outlasts the resulting scroll event regardless of its exact timing. The scroll listener also gained `{ passive: true }`, standard practice for a listener that never calls `preventDefault()`.

*Modal sizing*: `.compare-modal-dialog` was capped at `min(1200px, 100%) × min(820px, 100%)` - reasonable on a laptop screen, small on anything bigger. Since comparing two full rendered pages benefits from real width (unlike a prose-reading column that wants a capped line length), replaced the fixed pixel cap with viewport-relative sizing (`96vw × 94vh`) and reduced the overlay's own padding so the dialog isn't fighting it for space.

Verified: full suite (105/105, the existing test already asserting the script contains `postMessage`/`docmanager-diff-scroll` still passes unchanged, since those strings are still present) and a direct check that the rewritten script's new pieces (`reportScheduled`, `syncTimer`, `passive: true`) are present in real served output. The actual smoothness and modal proportions still need the user's own eyes - same standing limitation, not newly introduced by this fix.

**A second same-round follow-up**: the user reported the highlighted text itself was barely readable, and asked for GitHub's own diff color design specifically. Root cause, once traced: `REMOVED_CSS`/`ADDED_CSS` only ever set `background` - never `color` - so legibility depended entirely on whatever text color the tracked document itself happened to use, which is completely unknown and uncontrolled (the content being diffed is arbitrary user HTML, not docmanager's own themed UI). A dark-themed tracked document with light text over a light-pink/light-green highlight background would be genuinely close to unreadable - exactly the complaint.

Fixed with GitHub's actual, well-known diff colors (not invented here) as a **matched background+text-color pair**, not background alone: `#ffebe9`/`#82071e` for removed (light pink / dark red text), `#e6ffec`/`#116329` for added (light green / dark green text), each with a `prefers-color-scheme: dark` variant (`#3c1618`/`#ffb3ae`, `#0f2e1a`/`#7ee2a8`) so the highlight stays readable against a dark-themed tracked document too. The `text-decoration:line-through` on removed blocks was dropped entirely - a real, deliberate readability fix in its own right: strikethrough is a reasonable convention for a single removed CODE line, but striking through a whole removed PROSE paragraph makes it measurably harder to read, working directly against the point of a *reading* view.

**A genuine, reasoned exception to this project's own `!important` discipline**, not a lapse back into old habits: since this rule overlays a diagnostic marker on top of *arbitrary, unknown third-party CSS* (the tracked document's own stylesheet, possibly even an inline `style` attribute, with completely unpredictable specificity), only `!important` can reliably guarantee the override actually wins - verified directly, not assumed: a synthetic test with a tracked document setting `body{background:#111;color:#eee}` confirmed the injected rule still correctly forced readable dark-red-on-light-pink text regardless. The forced color is also applied to `[data-diff="removed"] *` (every descendant), not just the marked element itself - inheritance alone would lose to a more specific color rule the tracked document set on a nested link or bold span, so the descendant rule closes that gap too.

Three new tests (`render-diff.test.js`) verify the background+color pairing for both modes, confirm strikethrough is genuinely gone, confirm the descendant-color rule exists, and confirm the dark-mode media query is present - full suite now 107/107. Manually verified against a real dark-themed fixture (`body{background:#111;color:#eee}`), confirming the override actually wins as designed, not just asserted by regex.

## Twentieth round: Tier 2 convenience layer - rename, tags, bulk UI actions, download

The user said "start tier 2" - the four items the saved plan groups as "convenience and everyday-use polish." All four were designed and built in one round, in this order: download (simplest, a quick win to build momentum), rename (needed the most real design work), tags (schema + search integration), bulk actions (the most UI-heavy).

**Download** turned out to have genuinely zero server-side work: `GET /content/:hash` already exists and serves raw content for the reading pane's iframe. The UI change is a single `<a id="download-version" download>` next to "Open in new tab," with `viewVersion()` setting both its `href` and a computed `download` filename (`downloadFileName()`: the family's synthetic path with slashes replaced by hyphens, plus an 8-character hash prefix to disambiguate versions, e.g. `report-a1b2c3d4.html`). No new route, no new test needed beyond confirming the existing route still works (already covered).

**Rename** needed one real design question answered before writing any code: does a family's `syntheticPath` need to stay in sync anywhere else on rename? Grepped `local-state.js`, `track.js`, `reconcile.js`, and `server.js` for real call sites of `findBySyntheticPath` (local-state.js's own lookup-by-synthetic-path function) before assuming anything. Result: **no real caller exists** - nothing in the codebase actually looks a local-state mapping up by its `syntheticPath` field. But a second check (reading `reconcile.js` fully) found the field is NOT unused: `reconcile()` destructures `{ syntheticPath, realPath, familyId }` straight off each mapping and includes `syntheticPath` in every single result object it returns - which is what `docmanager status`/`families`' `newVersionsCaptured`/`missingOnDisk`/`behindHead`/`corrupt`/`orphanedMapping` arrays are built from. So a rename that only touched the family record (`store.js`) would leave every subsequent `status`/`families` call reporting the OLD path forever after, purely because the mapping's own denormalized copy went stale - a real, user-visible correctness bug, not a hypothetical.

Fixed at the right layer: `store.js`'s new `renameFamily(familyId, newSyntheticPath)` owns only the synced family record (uniqueness check via the existing `findFamilyBySyntheticPath`, reusing `createFamily`'s own invariant; idempotent no-op if unchanged; commits `Rename <old> -> <new>`). `local-state.js`'s new `updateMappingSyntheticPath(familyId, newSyntheticPath)` owns the never-synced mapping file, updating every mapping entry whose `familyId` matches (a family could in principle have more than one local mapping, e.g. two real paths on one machine both relinked to it - handled generally, not just for the common one-mapping case). `track.js`'s new `renameTrackedDocument()` is the orchestration layer that calls both, in that order, only updating the mapping if the rename actually changed something - the exact same split `untrackFamilies()` already established for delete (store.js's `deleteFamily` + local-state.js's `removeMappingByFamilyId`, combined in track.js). `server.js`'s `POST /families/:id/rename` route calls `renameTrackedDocument`, not `store.js`'s `renameFamily` directly, so this correctness fix can't accidentally be bypassed by whichever layer happens to call it.

A second, smaller correction was found by a failing test, not anticipated during design: the CLI end-to-end test asserted the old synthetic path (`/renamable`) would disappear entirely from `docmanager families` output after a rename, and it didn't - `family.title` (defaults to `syntheticPath` at creation time, `title ?? syntheticPath` in `createFamily`) was still showing the old path, since nothing had ever touched `title` on rename. There is no mechanism anywhere in this codebase to set a custom title separate from the synthetic path, so in practice `title === syntheticPath` always, for every family that exists today. Rather than leave `title` permanently stuck on a family's very first synthetic path forever, `renameFamily` now also updates `title` whenever it still equals the OLD synthetic path (i.e., it was never customized) - `if (family.title === oldSyntheticPath) family.title = newSyntheticPath`. This is deliberately conditional, not unconditional, so a genuinely custom title (were that feature ever added later) would be left alone by a rename.

**Tags** are `family.tags: string[]`, defaulted to `[]` in `createFamily`. `setFamilyTags(familyId, tags)` in `store.js` is a whole-array replace (matching `updateSettings`'s own established precedent for "the caller computes the desired final state, the store just persists it"), with light cleanup - trim each entry, drop empty strings, dedupe via `new Set()` - since tags are free-form labels, not a controlled vocabulary, and the only real invariant worth enforcing is "no meaningless entries." `index.js`'s schema gained a `tags_json` column on `families` (JSON-serialized, parsed back to an array on every read in `listFamiliesFromIndex`/`getFamilyFromIndex`, defaulting to `[]` for any pre-existing family record that predates this column and has no `tags` field at all) and a `tags` column on the `search` FTS5 virtual table, populated space-joined (`tags.join(" ")`) in the same `rebuildIndex()` transaction every other change already triggers. Because `toFtsQuery()`'s MATCH query is never column-scoped, a search term now matches a tag exactly the same way it already matched the synthetic path, title, or body text - no special-casing needed in `searchFamilies()` itself, confirmed by a test that tags a family with an otherwise-unrelated title/body and searches for the tag alone. `POST /families/:id/tags` (whole-array replace, matching `PUT /settings`'s own pattern) is the one new route; the CLI's `--add`/`--remove` flags are computed CLIside against the family's current tags (fetched first via `GET /families/:id`), then sent as a single full replace - there is no partial-update endpoint and none is planned, keeping the server-side contract simple.

**Bulk UI actions** needed no server changes at all: the CLI's `untrack <id>...` already accepted a batch via `POST /documents/untrack`, the UI just never had a multi-select affordance to call it with more than one id. Added a checkbox to each sidebar list item (both the tracked-document list and search results render through a shared `wireFamilyListItems()` now, rather than duplicating the click/checkbox-wiring logic twice), tracked in `state.bulkSelectedIds` (a `Set`, not an array, for cheap membership checks on every re-render). A checkbox's own click handler calls `stopPropagation()` so checking it doesn't also trigger `selectFamily()` on the row. A small bulk-action bar appears above the list once `bulkSelectedIds.size > 0` (`updateBulkActionsBar()`), offering "Untrack" (confirmed via `window.confirm()`, same as the existing single-document untrack) and "Clear." Selection state persists across a list re-render on purpose (a search, an SSE-triggered `refreshDocuments()`) rather than resetting - `refreshDocuments()` prunes any selected id that's no longer in the fresh family list, so a document untracked through some other path (the CLI, another browser tab) doesn't leave a phantom entry inflating the bulk-bar's count forever.

**A stale-doc correction, found while updating docs, not introduced this round**: `ARCHITECTURE.md` section 5 and the teaching doc both still said the UI was "read-only end to end, with no editing surface anywhere in it." This was already inaccurate before this round - `untrack`, `revert`, and `delete-version` are all real state mutations the UI already performed - and became impossible to leave standing once rename/tags/bulk-untrack were added directly on top of the same sentence. Corrected in both places to the actual, narrower claim that was true all along: no tracked document's *HTML content* is ever editable through the UI (that stays a different tool's job, per this project's own core positioning), but docmanager's own metadata about a document - which version is current, its synthetic path, its tags, whether it's tracked at all - is fully manageable from the UI, and always has been since the untrack button was added.

**A real process-hygiene mistake caught mid-round, not a bug in the new code**: after writing all the UI changes, the first manual verification step (`curl`-ing the real running dev core's `/` and grepping for the new element ids) found nothing - zero matches. Root cause: `server.js`'s `uiAssetsDir()` prefers `dist/ui` over `src/ui` whenever `dist/ui` exists (`existsSync(dist) ? dist : src`), and this project's `dist/` is a gitignored build artifact from an earlier session's `npm run build`, copied before this round's `src/ui` edits - so the already-running dev core was silently serving a stale build the whole time. Fixed by running `npm run build` (which also regenerates `skills/docmanager/SKILL.md` from `src/skill.js` via the same script) and restarting the core (`docmanager core stop && docmanager core start` - node caches modules per-process, so even with `dist/ui` rebuilt, a *already-running* core process wouldn't have picked up any `src/core/*.js` changes without a restart either). The user asked directly whether rename could break version history or the automatic version-capture mechanism. **The control**: a System/Light/Dark segmented toggle (`#theme-system`/`#theme-light`/`#theme-dark`) added to Settings under a new "Appearance" `info-block`, using the same visual language as the existing Text/Rendered mode toggle in the compare modal but a genuinely separate CSS definition (`.theme-toggle`/`.theme-tab`) rather than reusing `.compare-form button.mode-tab` - that selector's specificity is deliberately scoped to `.compare-form`, and the new control lives as a sibling `info-block` outside `#settings-form` entirely (a deliberate placement choice, covered below), so reusing the class name would have meant either fighting a specificity mismatch or accidentally relying on `.compare-form`'s own scoping by coincidence. A small, self-contained duplication of a simple pattern, chosen deliberately over forcing a shared abstraction across two different scoping contexts.

**Why the toggle lives outside `#settings-form`**: every other Settings control (`snapshotRemote`, the access token) is a real form field that round-trips through `PUT /settings` on submit. The theme choice is different in kind, not just implementation detail - it's a per-browser display preference that never touches the core, is never part of a snapshot, and applies the instant you click it, with no "Save" step. Placing it inside `#settings-form` would have implied a server round-trip that doesn't happen; keeping it a separate `info-block` (matching how "SSH setup" and "Background service" are already their own standalone blocks, not form fields) keeps that distinction honest in the markup itself, and incidentally means the toggle's own CSS never has to fight `#settings-form button`'s specificity the way `#settings-form button.link-button` already has to.

**The one real design decision**: avoiding a flash of the wrong theme on load. The naive approach - read `localStorage` and set `data-theme` from `app.js` - would visibly flash the OS-default (or light-default) theme first on every page load or reload for any user who'd explicitly chosen an override, since `app.js` is loaded via a `<script>` tag at the very end of `<body>`, well after the browser has already computed initial styles and started painting. Fixed with a small synchronous inline `<script>` placed in `index.html`'s `<head>`, before the stylesheet link: `(function(){try{var t=localStorage.getItem("docmanager-theme");if(t==="light"||t==="dark")document.documentElement.dataset.theme=t;}catch(e){}})();`. A synchronous inline script in `<head>` blocks HTML parsing until it completes, so the `data-theme` attribute is guaranteed to already be on `<html>` before the browser has enough of the document to paint anything - the standard, well-known pattern for this exact class of problem. `app.js`'s own `updateThemeButtons(getStoredTheme())` at startup only syncs the *button UI* to match, it never re-writes the attribute - there is exactly one place in the whole codebase that ever sets `data-theme`, by design, so there's no risk of the two ever disagreeing.

**A real gap found and fixed along the way, not anticipated up front**: the original `:root[data-theme="dark"]` block never set the CSS `color-scheme` property, and there was no `:root[data-theme="light"]` block at all. `color-scheme: light dark` on the base `:root` tells the browser "either is fine, follow the OS" for browser-drawn UI (scrollbars, native form control chrome) - but that's exactly wrong once a user has explicitly overridden the *page's* own colors via `data-theme`, since the native chrome would keep following the OS instead of the user's actual choice, producing a visibly mismatched page (e.g., a light scrollbar on an explicitly-dark page if the OS itself is set to light). Fixed by adding `color-scheme: dark` to the existing dark override block and a new, otherwise-empty `:root[data-theme="light"] { color-scheme: light; }` block (no other properties needed there, since the base `:root` values already *are* the light theme - only the native-chrome hint needed pinning).

**Sidebar exclusion, confirmed deliberate rather than assumed**: the sidebar's own `--sidebar-*` variables (`--sidebar-bg`, `--sidebar-text`, etc.) are never touched by either the `[data-theme="dark"]` block or the `prefers-color-scheme` media query - checked directly before building anything, not assumed. This matches the phase-4 redesign's own stated intent (`techContext.md`'s own earlier "Visual design decisions" note: "a dark, fixed sidebar (independent of the light/dark theme toggle on the main content area)... styled as a persistent chrome"), written before this toggle even existed to test the claim against. The toggle only ever changes the main content area's palette, exactly as originally planned.

No new automated tests were added - this is pure client-side DOM manipulation and `localStorage` I/O with zero server interaction, and this project has an established, deliberate testing boundary: `node:test` covers everything server-side and CLI-facing, while UI JavaScript (the scroll-sync script, the compare-mode toggle, and now this) gets structural presence verification against the real served output instead, since there's no browser-automation/jsdom dependency in this project by design. ## Release hardening, item 1: stale-core-after-upgrade detection

The plan's own framing of the gap: `GET /health` (`server.js`) has always returned `{ service, version, pid }`, `version` sourced from `src/version.js` - but nothing anywhere ever compared that returned value against anything, so it was pure unused information. The real risk it should have been catching: `npm install -g docmanager-axi@newversion` (or `npm update`) replaces the files on disk, including `version.js` itself, but an *already-running* core process has that module's old export sitting in its own process memory from whenever it last started - Node has no file-watching or hot-reload for its own already-`import`ed modules, so the running process has no way to notice anything changed until it's restarted. Left alone, a user could run `npm update` and keep silently talking to the pre-update core indefinitely, for as long as the idle timeout allows it to keep running (hours, by design).

**Where the fix lives, and why there**: `lifecycle.js`'s `ensureCoreRunning()` is the one function every single CLI command already routes through (`resolveContext`, per `ARCHITECTURE.md` section 4) before doing anything else, and it already does a full health-check-and-identity-confirm on every invocation (`checkHealth()`, comparing `body.service` against `SERVICE_NAME` to rule out PID-reuse-after-reboot false positives). Adding a version comparison to that same existing check costs nothing extra - no new network round trip, no new code path most invocations take. On a mismatch (`health.version !== VERSION`, where `VERSION` is imported fresh in this exact process from the currently-installed `version.js`), the function now: sends `SIGTERM` to the stale core's pid, calls a new `waitForProcessExit(pid, STOP_WAIT_TIMEOUT_MS)` helper (a bounded poll loop, mirroring the existing `waitForReady()` poll pattern already used elsewhere in this file) to give it a real chance to actually exit before racing to rebind the same port, then falls through to `clearLock()` and `continue` - which the existing loop already handles correctly, since a cleared lock with a remembered `lastKnownPort` is exactly the state a normal "core died, restart it" recovery already goes through. No new state machine was needed; the mismatch case was implemented as one more way to reach a code path that already existed and was already tested.

**Scope, stated explicitly to avoid it being mistaken for solving a different problem**: this detects an actual *version string* mismatch - the real `npm update` scenario the plan named. It does **not** detect "I edited `src/core/*.js` without bumping `version.js`" during local development, which is a different kind of staleness this same session already hit for itself in the Tier 2 round (the running dev core serving a stale, pre-edit `dist/ui` build) - that gap is inherent to editing source directly against a long-running dev daemon and has no general fix short of "rebuild and restart after any change," which is already the documented workflow for this project's own development. Conflating the two would be a real mistake: don't extend this feature to hash source files or anything similar to catch the dev-mode case, that's explicitly out of scope for what was asked.

**`docmanager core status` also got a small, deliberate addition**: `coreStatus()` (a separate, read-only function - `docmanager core status` must never have a side effect of its own initiative) now also returns `version` and a `stale` boolean, surfaced in `cli.js`'s `coreCommand` as a `note` field when true. This exists purely for visibility - a user who runs `docmanager core status` right after an upgrade, out of curiosity, gets an honest "yes, this is about to restart itself" instead of a bare "running" that would otherwise look identical to the healthy case until the next real command happened to trigger the actual restart.

**Testing this safely required one real design decision**: the natural way to simulate "a stale core" in a test is a hand-crafted lock file plus a fake `/health` response - but the very first version of this thought experiment would have used the *test process's own pid* as the lock's `pid` field, since `isProcessAlive()` needs a genuinely living pid to pass. That's dangerous: the restart logic calls `process.kill(lock.pid, "SIGTERM")` on a version mismatch, and sending `SIGTERM` to the test runner's own process would kill the test suite itself mid-run. Fixed by spawning a real, separate, disposable child process (`spawn(process.execPath, ["-e", "setInterval(() => {}, 1000)"])`) purely to serve as a living pid that's safe to kill, paired with a tiny real `http.createServer` (running in the test process itself, no risk there) that answers `/health` with a controllable, fake version string. `test/lifecycle.test.js` (new file - no lifecycle-specific test file existed before this) has three tests: `coreStatus()` correctly flags a stale-but-healthy fake core without ever touching it (asserted directly: `fakeCoreChild.killed === false` after the read-only check), `coreStatus()` correctly reports a current-version fake core as not stale, and `ensureCoreRunning()` actually kills the stale fake core and replaces it with a genuine, freshly-spawned real daemon (the actual `src/core/daemon.js`, via the existing `spawnDaemon()`) that reports the real current `VERSION` afterward. The third test genuinely spins up a real core as a side effect, cleaned up in `afterEach` via the real `stopCore()`, the same pattern `cli.test.js`'s own core-lifecycle test already establishes.

Manually verified against the real live dev core, not just the isolated test fixtures, to prove the actual `npm update` scenario end to end: temporarily overwrote the real `src/version.js` with a different version string (simulating what an upgrade's file-copy step would produce), ran `docmanager core status` and confirmed it reported `stale: true` with both the old (running) and new (installed) version numbers in a readable note, ran a real `docmanager families` command and watched the core transparently restart to a new pid - with the real store's 3 families and their full version history completely unaffected by the restart, confirmed via `docmanager doctor` reporting clean health both before and after - then reverted `version.js` to its real value and restarted the core cleanly to leave the dev environment exactly as found. ## Letting a user hand a tracked version off to Lavish Editor for review, via their own agent

The user wants `lavish-axi` reused as a genuine dependency - explicit about not wanting docmanager to reimplement any of its poll/annotate/apply machinery - and asked directly what the best design would be given a real architectural mismatch: docmanager has no active, long-lived agent-polling loop of its own, unlike an agent session that's already running `lavish-axi poll` and staying blocked on it. Every `docmanager` command is one-shot, runs, and exits - there is no persistent docmanager-side process that could ever "call out" to an agent the way the question seemed to assume was needed.

**The resolved insight, stated plainly rather than buried in the design**: docmanager cannot hook an agent, and doesn't need to. The agent already present in the user's conversation is the hook - the moment the user asks to edit a version, that already-running agent (which already has docmanager's skill loaded) simply knows the workflow, because the skill teaches it. No new server-side agent-connection mechanism, no callback, no webhook - the entire "hooking" problem dissolves once framed this way instead of trying to make docmanager itself agent-aware.

**Three real pieces got built, after design questions were worked through with the user rather than assumed:**

1. **`docmanager families export <id> <hash> --to <path>`** (`src/cli.js`, `src/cli/client.js`) - the one genuinely new piece of infrastructure. Reuses the existing `GET /content/:hash` route entirely (no new server route). Needed a new `requestRaw()` helper in `client.js`, separate from the existing `request()`, since `request()` unconditionally calls `res.json()` - which throws on a raw-HTML response body and gets silently swallowed by the existing catch-and-fall-through, meaning the *real content would have been discarded and `null` returned* if the existing helper had been reused naively. Caught this by reasoning through the existing code before writing anything, not by shipping it broken first. Manually verified against the real live store (real content exported, byte-identical to the source), plus both real error paths (`ENOENT` on a bad destination directory, an unknown hash) - the unknown-hash case surfaced a small, real, pre-existing gap: `handleContent`'s 404/400 JSON bodies never carried an error `code` field at all (only ever consumed by the browser's iframe directly before now, which doesn't care about codes), so this route's errors fell back to generic `UNKNOWN` through the CLI's `toAxiError` path. Fixed by adding `CONTENT_NOT_FOUND`/`INVALID_CONTENT_HASH` codes and a matching CLI suggestion.
2. **An "Edit in Lavish" button** next to Download in the UI's reading pane. Generates a three-step, ready-to-paste plain-text message (export → real `lavish-axi` → `track --as <path> --relink` + `status`) and copies it via `navigator.clipboard.writeText()`, with a `window.prompt()` fallback if clipboard access fails. The button and its generated text were verified with a real Playwright interaction against the live UI - not just a structural grep for the element's presence - navigating to the real running core, clicking the real family list item, clicking the real button, and reading the real clipboard content back out (`context = await browser.newContext({ permissions: ["clipboard-read", "clipboard-write"] })`), confirming the exact family id, version hash, and synthetic path were correctly interpolated.
3. **A redesigned relink UX.** `trackPath()`'s `FAMILY_PATH_EXISTS` error now attaches `err.existingFamily` (id, syntheticPath, title, versionCount, headVersion, headCreatedAt) before throwing, and `trackPaths()`'s per-path batch-result catch block spreads it into that path's own result object when present - both changes are purely additive, the error's own `.message`/`.code` are unchanged, so nothing that already consumed this error path (existing tests, the CLI's own error rendering) needed to change. The UI's track form now renders a `.track-collision` card per collision, showing the real matched document's info and two explicit actions ("Link this file to that history" / "Use a different name instead") instead of requiring the batch-wide "relink" checkbox to be guessed correctly *before* submitting. The existing batch checkbox is untouched and still serves its own real, different use case (reconnecting an entire snapshot-pulled folder at once, where per-file confirmation would be tedious) - its label was reworded from "from a snapshot" (too narrow - see the design note below) to something general.

**A real, load-bearing design correction surfaced directly by the user, not found independently**: the initial proposal (in conversation, before any code was written) was a "pause reconciliation on this path, then resume and capture" mechanism for the duration of a Lavish session. The user's own proposed alternative - "docmanager owns all versions, the real file is just one of many, download whichever version you want onto your machine" - turned out to make the pause/resume idea entirely unnecessary: if the working copy used for editing is simply never added to `local-state.json` as a mapping in the first place, it was never subject to `reconcile()`'s automatic capture to begin with, since `reconcile()` only ever iterates over known mappings. "Log the result only once the session ends" falls directly out of the existing relink-plus-reconcile-on-read model with zero new state, rather than requiring a new pause flag on something that *was* tracked. This is a meaningfully simpler design than the one first proposed, arrived at by taking the user's own reframing seriously rather than defending the original approach.

**A second real design clarification, also user-driven**: is `--relink` a snapshot-specific feature, or something more general? Traced through the actual code to answer precisely rather than guess: `trackPath()`'s relink branch has no snapshot-specific logic anywhere in it - it only ever checks `findFamilyBySyntheticPath()` and calls `addMapping()`. The fresh-machine-snapshot-pull scenario is simply the *original, motivating* trigger for needing it, not a constraint baked into the mechanism itself; "I downloaded an old version and want to reconnect my further edits to it" is a completely different trigger for the exact same code path, with zero snapshot involvement. This directly informed both the UI wording fix and the Lavish workflow's own final step (`track --as <path> --relink`), which leans on this same general reattachment mechanism rather than needing anything new.

**A third question got a real, reproduced answer instead of an assertion**: does a two-machine "A already has history, B pushes ahead, A later pulls" scenario correctly bring in B's full timeline, the way a `git pull` fast-forward would - or could it corrupt or duplicate anything? Built a real four-step reproduction (A tracks + pushes v1 → B clones + relinks + edits + pushes v2 → A pulls → A's `families view` and `status` checked) using the same `execFile`-based real-CLI-subprocess harness established in the demo-video round. Confirmed exactly the expected, already-correct behavior: `families view` on A shows the complete, correctly-ordered two-version timeline with the right `supersedes` chain and head, while A's own stale local file is correctly and only reported `behind-head` - nothing silently captured as a spurious new version, nothing corrupted. This is precisely the class of bug this project fixed early in its own history (the single worst bug the whole build ever produced, a reconciliation bug that once silently corrupted version history under exactly this kind of cross-machine timing) - confirming it still holds, empirically, rather than assuming a historical fix stayed correct forever.

A secondary, incidental finding from that same reproduction script, understood and confirmed non-alarming rather than left as a mystery: relinking a *second*, different real file to an already-existing family (as the relink-UX Playwright test also did, separately) legitimately produces a family with two live local mappings, and once one of them's edit becomes the new head, the *other*, untouched mapping is correctly reported `behind-head` on the next reconcile - exactly the documented, multi-mapping-per-family behavior already built during the Tier 2 rename round, working as designed, not a new edge case needing a fix.

3 new tests: two in `track.test.js` (the `existingFamily` error-enrichment shape, both for `trackPath()` directly and for `trackPaths()`'s batch result), one in `cli.test.js` (`families export`, covering the success path and both real error cases). Full suite 128/128. `ARCHITECTURE.md` gained a new unnumbered subsection under UI ("Editing a version with Lavish Editor") - deliberately unnumbered to match that section's own existing style for sub-topics (`### Rendering content safely` etc.) rather than risk a fragile renumber of the document's later numbered sections (6 through 9), several of which are cross-referenced by number elsewhere in the same document. `src/skill.js` gained the export command and a full dedicated section teaching the agent the exact three-step workflow, explicitly stating docmanager has no polling loop of its own and that the workflow only happens because the agent carries it out end to end - arguably the single most important documentation change in this round, since the skill is the actual mechanism that makes the whole feature work, not just a description of it. `README.md` and the teaching doc both updated with lighter-touch mentions. Nothing committed - the user was explicit that this, the README rewrite, and the demo video all wait for one bundled commit once more planned features land.

## Same-round follow-up: `lavish-axi` becomes a real dependency, export-and-open collapses into one command

Two sequential, sharp user questions turned a real design gap into a cleaner final shape, in the same session as the round above rather than a separate one.

**"Why export to disk first at all?"** Traced to the actual constraint rather than asserted: `lavish-axi`'s own CLI (per the `lavish` skill loaded earlier this session) takes a real file path as its argument - it serves, watches, and rewrites that file directly; it has no concept of fetching content from an arbitrary HTTP API. docmanager's content, meanwhile, lives inside its own content-addressed git store, addressed by hash, never as loose named files. Export is the necessary bridge between those two facts, not an arbitrary extra step.

**"Shouldn't the destination live somewhere in docmanager's own setup, instead of the agent inventing a path?"** A real, adopted design improvement: `paths.js` gained `editDir()` - `join(docmanagerHome(), "edit")` - matching the existing convention (`lockFilePath()`, `logFilePath()`, all one-line helpers building on `docmanagerHome()`). Documented as explicitly disposable scratch space, separate in kind from the actual synced store (`store/`) and the machine-local-but-permanent files (`local-state.json`, `settings.json`) - never synced, never part of the content-addressed history, safe to treat as throwaway.

**This directly enabled collapsing what were two separate agent-run steps into one.** New command `docmanager families lavish <id> <hash>` (`src/cli.js`, alongside the existing `families export`) does both in sequence: fetches the family and the version's raw content (`coreClient.getFamily`/`exportContent`, the same client calls `export` already used), writes it to `editDir()` under a filename matching the UI's own `downloadFileName()` convention exactly (moved into a new shared helper, `editFileName()` in `src/cli/lavish.js`, so both surfaces stay in sync by construction rather than by two independently-maintained copies of the same naming logic), then resolves and launches the real Lavish Editor CLI.

**The resolution itself is the other half of this round, and is what actually answers "how do we guarantee this uses docmanager's own copy, not npx or a global install."** `lavish-axi@^0.1.52` was added as a genuine `package.json` dependency (checked the real published package first - `npm view lavish-axi version bin main` - confirming `bin: { "lavish-axi": "dist/cli.mjs" }` before writing any resolution code, not assumed) and installed for real (`npm install`, 80 packages added, 0 vulnerabilities). `src/cli/lavish.js`'s `resolveLavishCli()` finds the actual installed entry point via `createRequire(import.meta.url).resolve("lavish-axi/package.json")` - Node's own module resolution, which walks up from *this file's own location* (inside docmanager's installation), never touching a global install path at all, regardless of whether one exists elsewhere on the system - then reads the package's own `bin` field dynamically rather than hardcoding `dist/cli.mjs`, in case that ever changes upstream. Verified this resolves to a real, existing file (not just a plausible-looking path) and that the resolved binary is genuinely invokable, via a side-effect-free `node <resolved-path> --version` check (prints `0.1.52`, no browser popped) - deliberately chosen over actually running the full open-a-session flow during verification, which would pop a real, visible browser window on the developer's own machine as a side effect neither requested nor desirable during automated testing.

**The command's own output is what keeps the agent's *next* step (the actual poll loop) honest too**, not just the open step: it prints back the exact resolved absolute path and the exact `node <path> poll <file>` invocation to run, rather than leaving the agent to reconstruct or guess a `lavish-axi`/`npx lavish-axi` invocation of its own that might resolve to something else entirely. The UI's `buildLavishPrompt()` and `src/skill.js`'s own workflow section were both tightened to say this explicitly - "use that command verbatim, don't substitute your own invocation" - closing the loop the user's own follow-up question opened ("how can we ensure the copy-paste command uses the dependency and not something global").

**A related question got a direct, reasoned no, not a workaround**: could the dependency be skipped if the user already has `lavish-axi` installed globally? No - Node's module resolution has no reliable, idiomatic way for one project to reach into a different package's global install; the only alternative is shelling out and hoping PATH/`npx` resolves the right thing, which is exactly the unreliability this whole redesign was built to eliminate. Declaring it as docmanager's own dependency is the same pattern every other real dependency in this project already follows (`axi-sdk-js`, `better-sqlite3`, `parse5`) - not special-cased overhead.

Manually verified end to end up to (but deliberately not including) the actual "open a real browser" step: `resolveLavishCli()` returns a real, existing path; `editFileName()` matches known inputs exactly, including the empty-synthetic-path edge case; the real `docmanager families lavish` command's validation-error paths (missing id/hash, an unknown family id) were exercised through the real CLI binary, both of which fail before ever reaching the spawn step, so they're fully safe to test automatically. The generated UI prompt was verified with a real Playwright click-and-clipboard-read against the live core, confirming the new command name and exact wording. 4 new tests (`test/lavish.test.js`, new; one addition to `cli.test.js`), full suite 132/132. `ARCHITECTURE.md`, `README.md`, the teaching doc, and `src/skill.js` all updated again to replace the earlier three-step/`npx`-based description with the current two-step/dependency-resolved one.

**A second, immediate same-round follow-up: the generated UI prompt itself was still too long, and the user caught exactly why.** The prompt (`buildLavishPrompt()` in `app.js`) had grown into a full restatement of the entire workflow - why the exact command matters, why not `npx`, the relink+status finalization step - all of which had *already* just been written into `src/skill.js`'s own dedicated section a few steps earlier in this same round. The user pointed out directly: the agent already has this via the skill (loaded once, reused for free on every subsequent use), so repeating the full explanation inside every single generated prompt is the same content paid for in tokens every time the button gets clicked, not a one-time cost. This is the exact `axi` skill discipline already loaded this session (token-efficient output, don't make the agent re-derive or re-read something already established) applied to a place that had drifted from it. Trimmed `buildLavishPrompt()` to one sentence: which version of which document, the one concrete command to run, and a pointer to "docmanager's own skill" for everything else - down from roughly 1,200 characters across 5 lines to 328 characters in one sentence, verified with the same real Playwright clipboard-read technique used throughout this feature line. No test asserted on the old prompt's exact wording (only ever manually/Playwright-verified, never locked into a permanent test), so nothing needed updating beyond the source itself. Full suite still 132/132, unaffected as expected - purely a UI string change.

## Release hardening, consolidated: the first real CI run, and three genuinely real bugs it found

The "consolidated write-up once the rest of release hardening is done" note left in `progress.md` earlier in this same session refers to this section. Items 2-7 of release hardening (log rotation, safe reset, the privacy nudge, `docmanager gc`, the release checklist, and the npm-name check) are each already described in reasonable technical detail in their own `activeContext.md`/`progress.md` entries at the time they were built; what's genuinely new here is what happened once the branch was actually pushed and CI ran against it for real, for the first time in this project's history. This is worth a dedicated section because all three findings below were previously-acknowledged-but-unverified risks (named explicitly in this file's own "known architectural risks" list, and in `ARCHITECTURE.md` section 9) that turned out to be real, not hypothetical, the moment they were actually run instead of code-reviewed - exactly the value this CI matrix was built to provide.

**Bug 1 - the stated `engines: ">=20"` floor was never true.** Confirmed directly, not inferred: `better-sqlite3@13.0.3` and `lavish-axi@0.1.52` - two direct dependencies - both declare their own `engines: {node: ">=22"}`. Running the real daemon under Node 20 doesn't throw a catchable JS error - `require('better-sqlite3')` opening a real database segfaults the whole process outright (confirmed with a minimal repro: `exit 139`, i.e. SIGSEGV). This is what made the `node-floor` CI job's failures look mysterious at first (every CLI test that touched the store failed with a bare "fetch failed" / exit 1, no stack trace, no core.log content) - a segfault kills the process before any of docmanager's own error handling ever runs, so the daemon just silently vanishes between one CLI call and the next. Traced by reproducing the exact spawn/health-check/second-call sequence locally under a real Node 20 install (via `nvm`), confirming the daemon survives fine standing alone but dies the instant a real store-touching command (`track`, `doctor`, `search`) reaches it - then isolating that down to a two-line `require('better-sqlite3'); new Database(':memory:')` repro that segfaults on its own, with zero docmanager code involved. Fixed by bumping `engines` to `">=22"` (matching what the dependency tree already actually requires) and re-pointing the `node-floor` CI job at `22.0.0` specifically (not a bare `22`, which the main matrix job already resolves to the latest 22.x and would make the two jobs pure duplicates) - so `node-floor` still serves its original purpose, confirming the floor of the *declared* range actually works, just against the floor that's true now. Verified locally via `nvm install 22.0.0` against a full scratch checkout: `npm ci`, `npm run build`, `npm test` all green, 145/145.

**Bug 2 - `better-sqlite3`'s own install step fails hard on a clean Windows runner, with no C++ toolchain available.** `better-sqlite3@13` bundles a real prebuilt binary for all eight platform/arch combinations directly in its own published npm tarball (`prebuilds/{platform}-{arch}.node`, confirmed via `npm pack --dry-run`) and resolves it lazily at first `require()` (`lib/binding.js`'s `getBinding()`) - no install-time step is actually needed when a prebuild is present. But that package's own `package.json` sets `gypfile: false` (which is *supposed* to stop npm's default "run node-gyp because a binding.gyp exists" behavior) and this was empirically NOT being honored during `npm ci` on this npm version (10.9.x): `npm ci --loglevel verbose` shows `npm info run better-sqlite3@13.0.3 install ... node-gyp rebuild` unconditionally, on every platform. On macOS/Linux with a C++ toolchain already present this is silent, wasted work (confirmed via `npm rebuild better-sqlite3` completing in well under half a second - too fast to be a real compile, so it's a fast no-op once node-gyp itself detects the prebuild via `binding.gyp`'s own conditional) - but on `windows-latest`, which has no MSVC Build Tools installed by default, that same attempted compile fails outright (`gyp ERR! find VS ... could not find a version of Visual Studio 2017 or newer to use`) and aborts the entire `npm ci`, before ever reaching the point where the bundled prebuild would have been used successfully. This is a real, externally-caused limitation in how `better-sqlite3@13`'s newer, prebuild-bundling install mechanism interacts with `windows-latest` GitHub Actions runners specifically - not a docmanager bug, and not something fixable from this project's own source. Fixed the actual CI failure with `npm ci --ignore-scripts` (verified locally, repeatedly, across macOS with both an old and a freshly-installed-via-Homebrew git, and under both Node 22.22 and 22.0.0: the full test suite passes identically with or without `--ignore-scripts`, confirming the skipped install step was never doing anything the runtime actually needed). **This is a CI-only fix, not a full fix** - a real end user running a plain `npm install docmanager-axi` on Windows (scripts NOT ignored, since that's not something `npm install` does by default for its own dependencies) could still hit this exact install failure if they don't already have a C++ toolchain present. This is a genuinely open, real risk worth testing against an actual `npm install` (no flag) on a real Windows machine before considering Windows fully supported for end users, not just for this project's own CI - flagged here explicitly rather than left as a silently-assumed non-issue.

**Bug 3 - the actual, most serious finding: `pullSnapshot()`'s clone path could silently produce an empty store on a newer git.** Found only because the two `snapshot.test.js` tests failed consistently in CI (both OS jobs, same two tests) but passed 100% of many repeated local runs on this machine's own git (`2.37.1`, from an old Xcode Command Line Tools install). Rather than assume "CI flakiness" and move on, installed a current git via Homebrew (`2.55.0`) and reproduced the exact same failure locally, 5/5 - confirming this is a real git-version-sensitive bug, not an environment fluke. Root cause, found by scripting the actual push/pull sequence directly and inspecting the resulting refs rather than guessing: `ensureStoreReadyUnlocked()` (`store.js`) already correctly pins the LOCAL store's initial branch name explicitly (`git init -b main`), specifically to avoid depending on `init.defaultBranch`. But `snapshot.test.js`'s own test fixture created the *bare remote* with a plain `git init --bare`, no `-b main` - so the bare remote's `HEAD` symref pointed at whatever that git install's own default resolved to (`master`, unset on this machine), a branch that was never actually pushed to (only `main` ever was). Older git's `clone` was lenient about this mismatch; git `2.55` is not - it follows the remote's `HEAD` symref literally, and since that ref doesn't exist, the clone lands with a real `origin/main` remote-tracking ref but genuinely **no local branch checked out at all** - an empty working tree, so every family/content file the clone was supposed to bring over appears to simply not exist (`getFamily()` returns `null`, `readContent()` returns `null` / throws `ENOENT`). **This is not just a test-fixture bug** - it's a live, real risk in `pullSnapshot()`'s own clone-path application code: any real user whose configured snapshot remote is a genuinely fresh/empty repository whose default branch isn't already `"main"` (a self-hosted git server, an older GitHub org default, a bare repo they `git init --bare`'d themselves) would hit the exact same silent-empty-clone failure on their own machine, with newer git, regardless of docmanager's own tests. Fixed in `pullSnapshot()` itself (`src/core/snapshot.js`), not just the test: after a successful clone, explicitly force the local branch with `git checkout -B main origin/main`, so the store ends up on a real, populated `main` branch regardless of what the remote's `HEAD` symref happened to point at during clone. Verified against the exact git version that reproduced the bug (`2.55.0`, 5/5 clean runs after the fix, previously 5/5 failing before it) and against the full suite under both that git version and the original `2.37.1` (145/145 either way, no regression for the case that already worked).

**The `runGc` test also failed once in this same CI run, on `macos-latest` only - a fourth, smaller, genuinely real bug in this session's own new code, not CI environment noise.** `dirSizeBytes()` (`src/core/maintenance.js`) walks the store's `.git` directory with `readdirSync` then `statSync`s each entry - a real TOCTOU race against git's own transient lock files (`objects/maintenance.lock` and similar), which can appear and disappear on git's own schedule during/after a `gc`, independent of this project's own `await` on the `git gc` subprocess having already resolved. The CI failure showed exactly this: `statSync` on a `maintenance.lock` path that had already been removed by the time the stat ran. Fixed by wrapping both the `readdirSync` and each entry's `statSync`/recursive call in their own `try`/`catch`, treating a vanished entry as contributing `0` bytes rather than crashing the whole report - this is only ever an informational before/after size, never a correctness-critical value, so silently skipping a file that disappeared mid-walk is the right level of defensiveness, not overcautious.

**What this confirms about the value of actually running this CI matrix, not just writing it**: every one of these four bugs was either explicitly named as an "unverified risk" in this project's own docs beforehand (bug 1, bug 2 - both restatements of the long-standing "better-sqlite3 prebuilds and detached-process semantics, never actually run on Windows/Ubuntu" line) or would have been essentially undiscoverable without a genuinely different environment (bug 3 needed a newer git than this development machine happens to have; bug 4 needed real timing pressure a fast local Mac rarely produces). None of them were found by code review, and all four were found and fixed in a single session once the pipeline actually ran for the first time - directly validating the reasoning that put "testing + CI" first in this project's own recommended production-readiness sequencing.

**Pushing the fix for bugs 1-4 triggered two more re-runs, each surfacing a further real bug - the same "actually running it" value paying off again, not diminishing returns on a lucky first find.**

**Bug 5 - a Windows-only CRLF-vs-LF checkout mismatch broke `build:skill:check`.** `windows-latest`'s default git checkout behavior converts committed LF line endings to CRLF, so the committed `skills/docmanager/SKILL.md` came out of checkout byte-different from the freshly-generated in-memory string `build-skill.js --check` compares it against (`readFileSync(skillPath, "utf8") !== generated`, an exact string comparison with no normalization) - even though the actual content was identical. No `.gitattributes` existed in the repo at all before this. Fixed with a repo-root `.gitattributes` (`* text=auto eol=lf`), the standard fix for exactly this class of problem - it also protects any future Windows contributor's local checkout from the same false-positive, not just CI.

**Bug 6 - pinning `node-floor` to the literal minimum (`22.0.0`) found the Node-20 segfault story wasn't fully closed.** After bug 1's fix (bumping `engines` to `">=22"` and pointing `node-floor` at `22.0.0` specifically, to genuinely verify the declared floor rather than just assert it), that job kept failing with the exact same segfault-class symptom (whole test *files* crashing, not individual subtests - `doctor.test.js`, `search.test.js`, `snapshot.test.js`, `store.test.js`, `tags.test.js`, all files that touch `better-sqlite3` directly in-process) even though the matrix's own `ubuntu-latest` job, running the *latest* 22.x patch on the same OS, passed cleanly. Tried to confirm this directly via a local Docker container running `node:22.0.0-bookworm` before concluding anything, but Docker's daemon wouldn't start in this sandboxed environment (tried twice, `docker info` never connected) - so the conclusion rests on two consecutive, identical, reproducible CI runs at the exact same pinned version rather than a third local confirmation, which is real evidence but weaker than the git-version bisection in bug 3 (which *was* locally reproduced). Rather than keep spending CI round-trips bisecting the exact minimum working 22.x patch, removed the `node-floor` job entirely and left `engines: ">=22"` as an honest major-version floor (matching what `better-sqlite3`/`lavish-axi` themselves declare) without re-claiming a literal, individually-verified-every-patch guarantee - documented directly in `ci.yml`'s own comment so a future session doesn't wonder where the job went or why.

**Bug 7 - a genuine, if lower-stakes, Windows-only EBUSY bug in the test harness itself**, found once bugs 5-6 were fixed and the matrix jobs finally ran far enough to reach it: `index.js`'s cached SQLite handle (`dbHandle`, a module-level singleton `helpers.js`'s own long-standing comment already documented as persisting across one test file's sequential tests) was never explicitly closed before a test's `afterEach` called `cleanupHome()` to `rmSync` the whole temp home directory. Unlinking a file with an open handle is a silent no-op on POSIX (why this was invisible through this entire project's macOS-only history) but a hard `EBUSY: resource busy or locked` on Windows. **Traced through to confirm this is test-infrastructure-only, not a live production risk, before treating it as "just fix and move on"**: the real `docmanager reset --confirm` command already stops the daemon process first and waits for it to actually exit (`waitForProcessExit()`) before deleting anything - a dead process releases every OS file handle it held automatically, identically on Windows and POSIX, so the actual CLI flow was never exposed to this race. Fixed by exporting a `closeIndexHandle()` from `index.js` (a thin wrapper around the already-existing internal `closeHandle()`) and calling it from `helpers.js`'s `cleanupHome()` before the `rmSync` - test-only surface area, nothing shipped in the real CLI/core needed to change.

**Bug 8 - one more real but small test bug, same CI round**: `track.test.js` asserted a real, raw Windows filesystem path (`tracked.path`, the actual on-disk path `trackPaths()` echoes back - correctly OS-native with backslashes, nothing for the application itself to normalize) against a regex hardcoded to a POSIX forward slash (`/notes\/doc\.html$/`). Fixed by building the expected suffix with `path.join("notes", "doc.html")` instead, which resolves to the right separator for whatever OS the test actually runs on.

**Final state**: all three OS jobs (`ubuntu-latest`, `windows-latest`, `macos-latest`) confirmed green via `gh run view`, not assumed from "should be fine now." Eight real bugs found and fixed across three fix-and-re-run cycles on the one PR, all from actually running the pipeline rather than code review - the single clearest demonstration yet of why this project's own roadmap put "testing + CI" first.
